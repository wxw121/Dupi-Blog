## 你会学到什么

- 建立分层根因分类。
- 从最终错误反向追踪执行轨迹。
- 保存可重放的 bad case。
- 用回归集验证修复没有制造新问题。
- 理解"一次只修一层"的调试原则。
- 设计 bad case 的数据结构和存储。

## 它解决什么问题

### 没有 Bad Case Debugging 的团队

```text
用户: "答案错了！"
开发: "哪里错了？"
用户: "它说退款期限是 30 天，实际是 7 天"
开发: "嗯...让我改改 prompt 试试"

（改了 prompt）
开发: "好了，你试试"
用户: "退款期限对了，但现在它不查订单状态了"
开发: "..."

（又改了 prompt）
开发: "这次应该好了"
用户: "订单状态有了，但引用标错了"
开发: "......"
```

**问题：不知道错在哪一层，只能盲目改 prompt。**

### 可能的根因

用户反馈"答案错了"，根因可能是：

```text
Query Planning 漏了子问题        ← 规划层
Retrieval Tool 查错索引          ← 检索层
ACL 过滤导致关键资料不可见       ← 权限层
重排把旧版文档放到前面           ← 排序层
业务工具返回缓存旧状态           ← 工具层
Citation Verification 漏检       ← 验证层
最终生成忽略证据                 ← 生成层
```

因此 **Bad Case Debugging** 必须串联 **Query Planning、Retrieval Tool、Citation Verification** 的全部数据。

## 核心概念：分层根因定位

### 类比：汽车故障诊断

| 症状 | 新手做法 | 专业技师做法 |
|---|---|---|
| 车不走了 | "换个电池试试" | 先检查油路→电路→点火→供油 |
| 答案错了 | "改改 prompt" | 先检查规划→检索→证据→验证→生成 |

专业技师不会一上来就换零件——他按照系统分层逐步排查。

### 反向追踪原则

```text
从最终错误向前追踪：

错误结论
  → 对应 claim 和引用是什么？
  → Citation Verification 结果如何？
  → Evidence Store 里有什么？
  → Retrieval Tool 的输入输出是什么？
  → Query Planning 生成了什么计划？
  → 用户原始任务和权限上下文是什么？
```

**从后向前，逐层定位，找到第一个出错的层。**

### 一次只修一层

```text
❌ 同时修改 prompt + 索引 + reranker
   → 答案变好了
   → 但不知道是哪个修改起了作用
   → 下次出问题时无法回溯

✅ 先固定其他层，只改一层
   → 确认是 Retrieval 的问题
   → 只修 Retrieval（调整 filter）
   → 验证修复有效
   → 再处理下一层
```

## 工程化版本

### 根因分类表

| 层级 | 常见根因 | 修复方向 |
|---|---|---|
| Input | 用户目标或实体缺失 | 增加澄清流程 |
| Query Planning | 漏子问题、错数据源、重复查询 | 改进 Planner prompt 或规则 |
| Retrieval Tool | 索引、filter、ACL、top_k 错误 | 修索引配置或 filter schema |
| Rerank | 旧版或无关文档排序过高 | 调整 reranker 或加版本权重 |
| Business Tool | 缓存旧状态、权限过滤错误 | 修缓存策略或权限配置 |
| Evidence | 去重、冲突、版本处理错误 | 修 Evidence Store 逻辑 |
| Citation Verification | 假引用、漏检 | 加强验证规则 |
| Generation | 忽略证据、错误归纳 | 改生成 prompt 或约束 |
| Orchestration | 循环、预算、停止条件错误 | 修编排逻辑 |

### 反向追踪实现

```python
class BadCaseDebugger:
    """
    Bad Case 调试器：从最终错误反向追踪。
    
    使用方式：
    1. 输入一个 bad case（错误答案 + 正确答案）
    2. 自动从后向前检查每一层
    3. 输出第一个出错的层和具体原因
    """

    def __init__(self, trace_store):
        self.trace_store = trace_store

    def diagnose(self, case_id: str) -> dict:
        """
        诊断一个 bad case。
        
        返回：{
            "root_cause_layer": "generation",
            "root_cause_detail": "模型忽略了 business_state 证据",
            "evidence": [...],
        }
        """
        trace = self.trace_store.get(case_id)

        # 从后向前检查
        # Layer 7: Generation
        if self._check_generation(trace):
            return {"root_cause_layer": "generation", "detail": "生成忽略证据"}

        # Layer 6: Citation Verification
        if self._check_citation(trace):
            return {"root_cause_layer": "citation", "detail": "验证漏检"}

        # Layer 5: Evidence
        if self._check_evidence(trace):
            return {"root_cause_layer": "evidence", "detail": "证据处理错误"}

        # Layer 4: Business Tool
        if self._check_tools(trace):
            return {"root_cause_layer": "business_tool", "detail": "工具返回错误"}

        # Layer 3: Retrieval
        if self._check_retrieval(trace):
            return {"root_cause_layer": "retrieval", "detail": "检索未召回"}

        # Layer 2: Query Planning
        if self._check_planning(trace):
            return {"root_cause_layer": "planning", "detail": "计划不完整"}

        # Layer 1: Input
        return {"root_cause_layer": "input", "detail": "输入信息不足"}

    def _check_generation(self, trace) -> bool:
        """检查生成层：证据充分但答案错误？"""
        # 如果证据都正确，但答案还是错 → 生成层问题
        return (
            trace.citation_passed
            and trace.evidence_sufficient
            and not trace.answer_correct
        )

    def _check_retrieval(self, trace) -> bool:
        """检查检索层：应该找到的没找到？"""
        expected_docs = trace.expected_evidence_ids
        actual_docs = [e.evidence_id for e in trace.evidence]
        missing = set(expected_docs) - set(actual_docs)
        return len(missing) > 0
```

### 可重放的 Bad Case

```python
@dataclass
class ReplayableBadCase:
    """
    可重放的 bad case：保存所有版本信息。
    
    重放时用相同版本执行，确保能复现问题。
    如果用最新版本重放，可能问题已经不存在了。
    """
    case_id: str
    task: str

    # 版本信息（重放必须）
    model_version: str          # 模型版本
    prompt_version: str         # prompt 模板版本
    tool_version: str           # 工具版本
    index_version: str          # 索引版本
    policy_version: str         # 策略版本

    # 执行上下文
    user_permissions: dict      # 用户权限（脱敏）
    random_seed: int | None     # 随机种子（如果有的话）

    # 预期结果
    expected_root_cause: str
    expected_tools: list[str]
    expected_evidence: list[str]
    forbidden_actions: list[str]

    # 脱敏快照（不包含真实敏感数据）
    snapshot: dict
```

**保存模型版本、prompt_version、tool_version、index_version、policy_version 和随机参数。敏感数据用脱敏快照。**

### 回归集

```python
class RegressionSuite:
    """
    回归测试集：确保修复不引入新问题。
    
    每个修复的 bad case 都加入回归集。
    每次修改后跑一遍回归集。
    """

    def __init__(self):
        self.cases: list[ReplayableBadCase] = []

    def add_case(self, case: ReplayableBadCase):
        """修复后把 case 加入回归集。"""
        self.cases.append(case)

    def run_all(self) -> dict:
        """
        跑所有回归案例。
        
        返回：{
            "total": 50,
            "passed": 48,
            "failed": [{"case_id": "BC-001", "reason": "..."}],
        }
        """
        results = []
        for case in self.cases:
            result = replay_and_verify(case)
            results.append(result)

        passed = [r for r in results if r.passed]
        failed = [r for r in results if not r.passed]

        return {
            "total": len(results),
            "passed": len(passed),
            "failed": failed,
        }
```

### 一次只修一层

如果 Retrieval Tool 没召回，不要先改最终 prompt。先用固定 query 验证索引、filter 和重排：

```python
def debug_retrieval_layer(case: ReplayableBadCase):
    """
    单独调试检索层。
    
    固定输入（query），只检查检索输出。
    排除其他层的干扰。
    """
    # 用固定的 query（不经过 Planner）
    fixed_query = {
        "query_id": "debug-q1",
        "question": "高级报表套餐要求",
        "source": "product_docs",
        "filters": {"version": "current"},
    }

    # 执行检索
    results = retrieval_tool.retrieve(fixed_query)

    # 检查：期望的文档在不在结果中？
    expected_doc = "product_manual_v3.pdf#page42"
    found = any(r.source == expected_doc for r in results)

    if not found:
        # 检索层确实有问题
        print("检索层问题：期望文档未被召回")
        print(f"索引版本: {case.index_version}")
        print(f"Filter: {fixed_query['filters']}")
        # → 可能是索引没更新，或 filter 排除了
    else:
        print("检索层正常：文档已召回")
        # → 问题在其他层（rerank？生成？）
```

## 常见失败模式

### 1. 只保存最终答案

```text
❌ 保存: {"question": "...", "answer": "..."}
   → 无法定位是哪一层出了问题

✅ 保存: 完整 trace（query_plan + retrievals + tools + evidence + citation + answer）
```

### 2. 所有 bad case 都归因"模型幻觉"

```text
"答案错了" → "模型幻觉" → "改 prompt"
但实际上可能是：
- 检索没找到正确文档（检索层）
- 找到了但 rerank 排到后面（排序层）
- 证据正确但生成忽略了（生成层）

不是所有错误都是"幻觉"！
```

### 3. 同时修改 prompt、索引和 reranker

```text
修改后答案好了 → 但不知道哪个修改有效
下次类似问题 → 不知道该怎么修
```

### 4. 回放使用了最新文档而非当时版本

```text
Bad case 发生时：索引是 v8
回放调试时：索引已经更新到 v12
→ 问题可能已经不存在了（但也没有真正修复）
```

### 5. 没有用户权限上下文

```text
用户 A（管理员）能看到文档 X
用户 B（普通用户）看不到文档 X
Bad case 来自用户 B，但调试时用管理员账号回放
→ 复现不了问题！
```

### 6. 修复一个案例后没有跑回归集

```text
修了 BC-001 → 答案好了
但 BC-015 的答案变差了（因为修改影响了其他场景）
→ 没有回归集就发现不了
```

## 什么时候不要这么做

**不要把真实敏感数据直接复制进公共测试集。**

```text
❌ 把用户的真实订单数据放进回归集
✅ 脱敏后保存（订单号替换、金额保留、姓名去除）
```

**随机不可复现的线上轨迹如果缺版本信息，应先补观测，不要假装已找到根因。**

```text
如果 trace 中没有 index_version：
→ 不知道当时用的是哪个索引
→ 无法确定是索引问题还是其他问题
→ 先补观测，下次复现时才能定位
```

**不要用单个 bad case 推导全局架构结论；先看同类错误频率。**

```text
一个 case 的检索没召回 → 可能是偶发
50 个 case 都是检索没召回 → 系统性问题，需要修架构
```

## 生产环境注意事项

- Bad case 数据脱敏并受访问控制（不是所有人都能看）。
- 保存必要版本和决策摘要（可重放）。
- 给每个修复绑定 root_cause 和 regression_cases（可追溯）。
- 区分数据问题、配置问题和代码问题（修复方式不同）。
- 修复上线后监控同类错误率（确认修复有效）。
- Bad case 提交时需要 trace_id（关联完整轨迹）。
- 回归集定期清理（过时的 case 标记为 archived）。

## 如何观测和评测

维护回归表：

```text
case_id              ← 唯一标识
root_cause           ← 根因分类
expected_tools       ← 期望调用哪些工具
expected_evidence    ← 期望召回哪些证据
forbidden_actions    ← 不允许的操作
expected_stop_reason ← 期望的停止原因
expected_claims      ← 期望的答案声明
```

指标：

| 指标 | 含义 | 健康范围 |
|---|---|---|
| 根因分类覆盖率 | 能归因到具体层的比例 | > 90% |
| 可重放率 | 能成功重放的比例 | > 80% |
| 平均定位时间 | 从发现到定位根因的时间 | < 2h |
| 修复后通过率 | 修复后回归集通过率 | > 95% |
| 新增回归数 | 每次修复引入的新问题数 | 0 |
| 同类问题复发率 | 修复后同类问题再次出现 | < 5% |

## 和 RAG / 后端 / 前端的关系

- RAG 暴露查询、filter、召回和重排版本（调试需要）。
- 后端保存完整 trace 和 Policy 决策（回放需要）。
- 前端反馈入口附带 trace_id（用户点"答案有误"时自动关联）。
- Citation Verification 结果直接进入 bad case（验证失败自动创建 case）。

## 面试怎么讲

> 我会从错误 claim 反向追踪引用、Evidence Store、Retrieval Tool、Query Planning 和原始输入，按层定位。bad case 保存模型、prompt、tool、index 和 policy 版本，修复时一次只改一层，并把案例加入回归集。没有完整轨迹时先补观测，不先猜 prompt。
