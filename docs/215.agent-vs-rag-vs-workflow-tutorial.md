## 你会学到什么

- 区分四种系统形态：普通 API、RAG、Workflow、Agent。
- 建立选型决策树（不是"越高级越好"）。
- 理解每种形态的成本、复杂度、适用场景。
- 设计混合架构（一个系统中同时使用多种形态）。
- 避免"为了用 Agent 而用 Agent"。

## 它解决什么问题

### 选型混乱的现状

```text
常见错误：

错误 1：所有需求都用 Agent
  "帮我查个天气" → Agent 循环 5 步 → 耗时 10 秒
  其实一个 API 调用 0.5 秒就搞定

错误 2：该用 Agent 时用了 Workflow
  "帮我处理这个客户问题"（需要动态判断）
  → 写死流程 → 遇到新情况就卡住

错误 3：该用 Workflow 时用了 Agent
  "每天凌晨备份数据库"（固定步骤）
  → Agent 每次都要"思考" → 浪费 token
  → 而且可能"想出"不同的执行方式（不确定性！）

正确思路：
  用最简单的形态解决问题。
  能用 API 就不用 RAG，能用 RAG 就不用 Workflow，
  能用 Workflow 就不用 Agent。
```

## 四种形态详解

### 形态 1：普通 API

```text
特征：
  - 确定性输入 → 确定性输出
  - 不需要 LLM
  - 延迟 < 100ms
  - 100% 可预测

适用场景：
  - CRUD 操作
  - 数据查询
  - 格式转换
  - 认证鉴权

示例：
  GET /users/123 → {"name": "张三", "email": "..."}
  POST /orders → {"order_id": "ORD-001"}

成本：几乎为零
复杂度：低
```

### 形态 2：RAG

```text
特征：
  - 需要 LLM 生成自然语言
  - 输入是问题，输出是回答
  - 一次 LLM 调用
  - 延迟 1-3 秒
  - 结果有随机性但可控

适用场景：
  - 知识问答
  - 文档摘要
  - 内容生成
  - 翻译

示例：
  "什么是向量数据库？" → 检索文档 → 生成回答

成本：1 次 LLM 调用（~$0.01）
复杂度：低-中
```

### 形态 3：Workflow

```text
特征：
  - 固定步骤，预定义流程
  - 步骤之间可能有条件分支
  - 但分支是预先写好的
  - 不需要 LLM 做决策
  - 延迟取决于步骤数

适用场景：
  - 文档处理管道（上传→解析→分块→索引）
  - 定时任务（备份、清理、报告）
  - 审批流程（提交→审核→批准→执行）
  - ETL 管道

示例：
  文件上传 → 格式检测 → 内容提取 → 分块 → 向量化 → 存储

成本：取决于步骤（可能包含 LLM 调用）
复杂度：中
```

### 形态 4：Agent

```text
特征：
  - 动态决策（下一步做什么由 LLM 决定）
  - 多步执行，步数不确定
  - 能调用工具
  - 有记忆和状态
  - 能自我纠错
  - 延迟 3-60 秒

适用场景：
  - 复杂任务（需要动态规划）
  - 多系统协调
  - 条件复杂（无法预定义所有分支）
  - 需要自我纠错

示例：
  "分析这个 bug 并修复" → 读代码 → 定位问题 → 修改 → 测试 → 验证

成本：N 次 LLM 调用（~$0.05-0.5）
复杂度：高
```

### 对比总表

```text
维度        API       RAG       Workflow    Agent
────────────────────────────────────────────────────
LLM 调用    0         1         0-N（固定）  N（动态）
延迟        <100ms    1-3s      1-30s       3-60s
确定性      100%      ~90%      ~95%        ~70%
成本        ~0        $0.01     $0.01-0.1   $0.05-0.5
复杂度      低        低-中     中          高
灵活性      无        低        中          高
适用        数据操作  知识问答  固定流程    动态任务
```

## 选型决策框架

### 决策树

```text
开始
│
├─ 需要自然语言生成吗？
│  ├─ 否 → 普通 API
│  └─ 是 ↓
│
├─ 需要多步操作吗？
│  ├─ 否 → RAG
│  └─ 是 ↓
│
├─ 步骤是固定的吗？
│  ├─ 是 → Workflow
│  └─ 否 ↓
│
├─ 需要动态决策吗？
│  ├─ 否 → Workflow（带条件分支）
│  └─ 是 → Agent
│
└─ 最终确认：
   用最简单的能解决问题的形态。
```

### 实际案例分析

```text
案例 1："帮我查一下订单状态"
  分析：单次查询，不需要 LLM
  选择：普通 API
  实现：GET /orders/{id}/status

案例 2："解释一下我们的退货政策"
  分析：需要自然语言回答，单次
  选择：RAG
  实现：检索政策文档 → 生成回答

案例 3："上传文件并建立索引"
  分析：多步但固定（上传→解析→分块→索引）
  选择：Workflow
  实现：Celery task chain

案例 4："分析这个客户的问题，查订单，如果符合条件就退款"
  分析：多步 + 条件判断 + 需要理解自然语言
  选择：Agent
  实现：Agent 循环 + 工具（查订单、退款）

案例 5："每天早上生成运营报告"
  分析：多步但固定（拉数据→计算→生成→发送）
  选择：Workflow（定时触发）
  实现：Cron + 管道

案例 6："帮我调研竞品并写分析报告"
  分析：多步 + 动态（不知道要搜几次）+ 需要综合
  选择：Agent
  实现：研究 Agent（参考 251）
```

## 最小示例

### 四种形态的代码对比

```python
from dataclasses import dataclass, field
from typing import Any, Callable
from enum import Enum


# === 形态 1：普通 API ===

def get_order_status(order_id: str) -> dict:
    """普通 API：确定性查询。"""
    # 模拟数据库查询
    orders = {
        "ORD-001": {"status": "shipped", "eta": "2024-03-15"},
        "ORD-002": {"status": "processing", "eta": "2024-03-18"},
    }
    return orders.get(order_id, {"error": "not found"})


# === 形态 2：RAG ===

def rag_answer(question: str, documents: list[str]) -> str:
    """RAG：检索 + 生成。"""
    # 检索
    relevant = [d for d in documents if any(w in d for w in question.split())]
    context = "\n".join(relevant[:3])
    # 生成（简化）
    return f"根据文档：{context[:100]}...\n回答：这是关于「{question}」的信息。"


# === 形态 3：Workflow ===

@dataclass
class WorkflowStep:
    name: str
    fn: Callable
    retries: int = 2


class Workflow:
    """固定流程 Workflow。"""

    def __init__(self, name: str):
        self.name = name
        self.steps: list[WorkflowStep] = []

    def add_step(self, name: str, fn: Callable, retries: int = 2):
        self.steps.append(WorkflowStep(name=name, fn=fn, retries=retries))

    def execute(self, input_data: Any) -> dict:
        """按顺序执行所有步骤。"""
        current = input_data
        results = []

        for step in self.steps:
            success = False
            for attempt in range(step.retries + 1):
                try:
                    current = step.fn(current)
                    results.append({"step": step.name, "status": "ok"})
                    success = True
                    break
                except Exception as e:
                    if attempt == step.retries:
                        results.append({"step": step.name, "status": "failed", "error": str(e)})
                        return {"success": False, "results": results, "failed_at": step.name}

        return {"success": True, "results": results, "output": current}


# === 形态 4：Agent ===

class SimpleAgent:
    """动态决策 Agent。"""

    def __init__(self, tools: dict[str, Callable]):
        self.tools = tools
        self.max_steps = 10

    def run(self, goal: str) -> dict:
        """Agent 循环。"""
        history = []
        state = {"goal": goal, "done": False}

        for step in range(self.max_steps):
            # 决策（简化：规则引擎）
            action = self._decide(state, history)

            if action["type"] == "finish":
                return {"goal": goal, "result": action["answer"], "steps": step + 1}

            # 执行工具
            tool_fn = self.tools.get(action["tool"])
            if tool_fn:
                result = tool_fn(**action.get("params", {}))
                history.append({"tool": action["tool"], "result": result})
                state["last_result"] = result

        return {"goal": goal, "result": "超时", "steps": self.max_steps}

    def _decide(self, state: dict, history: list) -> dict:
        """决策逻辑。"""
        goal = state["goal"].lower()

        if not history:
            if "订单" in goal:
                return {"type": "tool", "tool": "query_order", "params": {"order_id": "ORD-001"}}
            elif "退" in goal:
                return {"type": "tool", "tool": "refund", "params": {"amount": 89}}

        return {"type": "finish", "answer": f"已完成：{state.get('last_result', goal)}"}


# 演示
def demo_four_forms():
    print("=== 形态 1：API ===")
    print(f"  {get_order_status('ORD-001')}")

    print("\n=== 形态 2：RAG ===")
    docs = ["向量数据库用于语义检索", "RAG 是检索增强生成"]
    print(f"  {rag_answer('向量数据库', docs)[:60]}...")

    print("\n=== 形态 3：Workflow ===")
    wf = Workflow("document_processing")
    wf.add_step("parse", lambda x: f"parsed:{x}")
    wf.add_step("chunk", lambda x: f"chunked:{x}")
    wf.add_step("index", lambda x: f"indexed:{x}")
    result = wf.execute("report.pdf")
    print(f"  {result}")

    print("\n=== 形态 4：Agent ===")
    agent = SimpleAgent({
        "query_order": lambda order_id="": f"订单 {order_id}: 已发货",
        "refund": lambda amount=0: f"退款 {amount} 元成功",
    })
    result = agent.run("帮我查订单状态")
    print(f"  {result}")
```

## 工程化版本：混合架构

### 统一路由器

```python
class SystemRouter:
    """系统路由器：根据请求类型分发到不同处理器。"""

    def __init__(self):
        self._routes: dict[str, Callable] = {}
        self._default = None

    def register(self, pattern: str, handler: Callable):
        self._routes[pattern] = handler

    def set_default(self, handler: Callable):
        self._default = handler

    def route(self, request: dict) -> dict:
        """路由请求。"""
        request_type = request.get("type", "unknown")

        # 精确匹配
        if request_type in self._routes:
            return self._routes[request_type](request)

        # 关键词匹配
        query = request.get("query", "").lower()
        for pattern, handler in self._routes.items():
            if pattern in query:
                return handler(request)

        # 默认
        if self._default:
            return self._default(request)

        return {"error": "no handler found"}


class HybridArchitecture:
    """混合架构：一个系统包含所有形态。"""

    def __init__(self):
        self.router = SystemRouter()
        self._setup_routes()

    def _setup_routes(self):
        """配置路由。"""
        # 简单查询 → API
        self.router.register("query", self._handle_api)
        # 知识问答 → RAG
        self.router.register("knowledge", self._handle_rag)
        # 固定流程 → Workflow
        self.router.register("process", self._handle_workflow)
        # 复杂任务 → Agent
        self.router.register("task", self._handle_agent)
        # 默认 → RAG
        self.router.set_default(self._handle_rag)

    def handle(self, request: dict) -> dict:
        """统一入口。"""
        return self.router.route(request)

    def _handle_api(self, request: dict) -> dict:
        return {"mode": "api", "result": get_order_status(request.get("id", ""))}

    def _handle_rag(self, request: dict) -> dict:
        docs = ["RAG 文档内容..."]
        return {"mode": "rag", "result": rag_answer(request.get("query", ""), docs)}

    def _handle_workflow(self, request: dict) -> dict:
        wf = Workflow("task")
        wf.add_step("step1", lambda x: x)
        wf.add_step("step2", lambda x: x)
        return {"mode": "workflow", "result": wf.execute(request.get("input"))}

    def _handle_agent(self, request: dict) -> dict:
        agent = SimpleAgent({"search": lambda q="": f"results for {q}"})
        return {"mode": "agent", "result": agent.run(request.get("query", ""))}
```

### 成本感知路由

```python
@dataclass
class RouteDecision:
    """路由决策（带成本估算）。"""
    target: str
    estimated_cost: float  # 美元
    estimated_latency: float  # 秒
    confidence: float


class CostAwareRouter:
    """成本感知路由器。"""

    COST_TABLE = {
        "api": {"cost": 0.0, "latency": 0.05},
        "rag": {"cost": 0.01, "latency": 2.0},
        "workflow": {"cost": 0.05, "latency": 10.0},
        "agent": {"cost": 0.20, "latency": 30.0},
    }

    def __init__(self, budget_per_request: float = 0.5):
        self.budget = budget_per_request

    def decide(self, query: str) -> RouteDecision:
        """做路由决策。"""
        # 简化分类
        if self._is_simple_query(query):
            target = "api"
            confidence = 0.9
        elif self._is_knowledge_query(query):
            target = "rag"
            confidence = 0.85
        elif self._is_fixed_process(query):
            target = "workflow"
            confidence = 0.8
        else:
            target = "agent"
            confidence = 0.7

        # 成本检查
        cost_info = self.COST_TABLE[target]
        if cost_info["cost"] > self.budget:
            # 降级
            target = "rag"
            cost_info = self.COST_TABLE[target]

        return RouteDecision(
            target=target,
            estimated_cost=cost_info["cost"],
            estimated_latency=cost_info["latency"],
            confidence=confidence,
        )

    def _is_simple_query(self, q: str) -> bool:
        return any(kw in q for kw in ["查", "获取", "状态"])

    def _is_knowledge_query(self, q: str) -> bool:
        return any(kw in q for kw in ["什么", "怎么", "如何", "为什么"])

    def _is_fixed_process(self, q: str) -> bool:
        return any(kw in q for kw in ["上传", "处理", "导出", "备份"])
```

## 常见失败模式

### 1. 过度工程

```text
场景：
  "查个用户信息" → 用 Agent 循环 3 步

后果：
  延迟从 50ms 变成 10s
  成本从 $0 变成 $0.1
  用户体验极差

解决：
  永远先问：最简单的方案是什么？
  能用 API 就不用 RAG，能用 RAG 就不用 Agent。
```

### 2. 该用 Agent 时用了 Workflow

```text
场景：
  客服流程写死了 5 步
  用户问了一个流程外的问题 → 系统卡住

后果：
  用户体验差，频繁转人工

解决：
  如果分支 > 10 个，考虑用 Agent。
  Workflow 适合"可枚举"的流程。
  Agent 适合"不可枚举"的流程。
```

### 3. 混合架构中路由错误

```text
场景：
  复杂任务被路由到 RAG → 回答不完整
  简单查询被路由到 Agent → 浪费资源

后果：
  成本浪费 + 体验不一致

解决：
  1. 路由层用轻量模型（不用大模型做路由）
  2. 收集路由错误案例，持续优化
  3. 允许降级（Agent 失败 → 转人工）
```

### 4. Workflow 中嵌入不必要的 LLM

```text
场景：
  固定流程的每一步都调用 LLM "确认"

后果：
  成本翻倍，延迟翻倍，但结果一样

解决：
  Workflow 中只在"需要生成自然语言"的步骤用 LLM。
  数据转换、格式处理用确定性代码。
```

## 什么时候不要这么做

```text
不需要混合架构的场景：

1. 产品功能单一
   只有一个知识问答 → 纯 RAG 即可
   不需要路由、不需要 Agent

2. 团队规模小
   1-2 人维护 → 越简单越好
   混合架构的运维成本高

3. 流量极小
   每天 100 个请求 → 成本不是问题
   全用 Agent 也无所谓

4. 需求不明确
   还不知道用户会问什么
   先用 RAG 跑起来，再根据数据决定
```

## 生产环境注意事项

### 监控分层

```text
每层有不同的监控重点：

API 层：
  - 响应时间 P99
  - 错误率
  - QPS

RAG 层：
  - 检索命中率
  - 生成质量（用户反馈）
  - Token 消耗

Workflow 层：
  - 完成率
  - 每步耗时
  - 失败步骤分布

Agent 层：
  - 任务完成率
  - 平均步数
  - 工具调用成功率
  - 超时率
```

### 降级策略

```text
降级链：
  Agent 失败 → 降级为 Workflow
  Workflow 失败 → 降级为 RAG
  RAG 失败 → 降级为模板回答
  全部失败 → 转人工

每层降级都要：
  1. 记录原因
  2. 通知用户（"当前使用简化模式"）
  3. 触发告警
```

## 如何观测和评测

### 路由准确率

```text
评测方法：
  1. 标注 100 个请求的"正确形态"
  2. 运行路由器
  3. 计算准确率

目标：
  路由准确率 > 90%
  误路由到更贵形态 < 5%（浪费）
  误路由到更便宜形态 < 10%（质量下降）
```

### 各形态 SLA

```text
形态      延迟 P99    可用性    错误率
─────────────────────────────────────
API       100ms       99.99%    < 0.1%
RAG       3s          99.9%     < 1%
Workflow  30s         99.5%     < 2%
Agent     60s         99.0%     < 5%
```

## 和 RAG / 后端 / 前端的关系

```text
与 RAG 的关系：
  RAG 是四种形态之一
  在混合架构中，RAG 处理知识问答
  Agent 可以把 RAG 作为工具调用

与后端的关系：
  路由层是后端的一个中间件
  各形态的处理器是独立服务
  统一 API 网关对外

与前端的关系：
  前端不需要知道后端用了哪种形态
  统一接口：POST /chat {"query": "..."}
  后端自动路由
  前端只展示结果 + 延迟提示
```

## 面试怎么讲

```text
问：Agent、RAG、Workflow 怎么选？

答（30 秒版）：
  四种形态：API、RAG、Workflow、Agent，复杂度递增。
  选型原则：用最简单的能解决问题的。
  不需要 LLM → API。一问一答 → RAG。
  固定多步 → Workflow。动态决策 → Agent。
  实际系统是混合的：路由层根据请求类型分发。

追问 1：为什么不全部用 Agent？
  → 成本、延迟、确定性。
    简单查询用 Agent 是 10 秒 + $0.2，用 API 是 50ms + $0。
    而且 Agent 有随机性，固定流程不需要随机性。

追问 2：怎么决定一个需求用哪种？
  → 决策树：需要 LLM 吗？需要多步吗？步骤固定吗？需要动态决策吗？
    四个问题问完就知道用哪种。

追问 3：实际系统怎么组织？
  → 混合架构 + 统一路由。
    前端统一接口，后端路由层分发。
    降级链：Agent → Workflow → RAG → 模板 → 人工。
```

### 选型评估表

```python
class ArchitectureSelector:
    """架构选型评估器。"""

    CRITERIA = [
        ("needs_llm", "需要自然语言生成？", ["api"]),
        ("multi_step", "需要多步操作？", ["api", "rag"]),
        ("fixed_steps", "步骤是否固定？", ["agent"]),
        ("dynamic_decision", "需要动态决策？", ["api", "rag", "workflow"]),
        ("self_correction", "需要自我纠错？", ["api", "rag", "workflow"]),
    ]

    def evaluate(self, answers: dict[str, bool]) -> str:
        """根据答案评估最佳架构。"""
        if not answers.get("needs_llm", False):
            return "api"
        if not answers.get("multi_step", False):
            return "rag"
        if answers.get("fixed_steps", False) and not answers.get("dynamic_decision", False):
            return "workflow"
        if answers.get("dynamic_decision", False) or answers.get("self_correction", False):
            return "agent"
        return "workflow"  # 默认

    def explain(self, choice: str) -> str:
        """解释选择原因。"""
        explanations = {
            "api": "不需要 LLM，确定性操作，用普通 API 即可。",
            "rag": "需要自然语言生成，但单次完成，用 RAG。",
            "workflow": "多步但固定，不需要动态决策，用 Workflow。",
            "agent": "需要动态决策或自我纠错，用 Agent。",
        }
        return explanations.get(choice, "")


# 使用
def demo_selector():
    selector = ArchitectureSelector()

    scenarios = [
        {"name": "查询用户信息", "answers": {"needs_llm": False}},
        {"name": "解释退货政策", "answers": {"needs_llm": True, "multi_step": False}},
        {"name": "文档索引管道", "answers": {"needs_llm": True, "multi_step": True, "fixed_steps": True}},
        {"name": "智能客服", "answers": {"needs_llm": True, "multi_step": True, "dynamic_decision": True}},
    ]

    print("\n=== 选型评估 ===")
    for s in scenarios:
        choice = selector.evaluate(s["answers"])
        reason = selector.explain(choice)
        print(f"  {s['name']} → {choice.upper()}")
        print(f"    原因: {reason}")
```

### 团队能力与选型

```text
选型还要考虑团队能力：

团队 1-2 人：
  推荐：API + RAG
  原因：维护简单，出问题容易排查
  避免：Agent（调试困难）

团队 3-5 人：
  推荐：API + RAG + Workflow
  原因：Workflow 可控，测试容易
  避免：复杂 Agent（没有精力维护）

团队 5+ 人：
  推荐：混合架构
  原因：有专人负责 Agent、监控、评测
  注意：仍然从简单开始，逐步演进

关键原则：
  架构复杂度 ≤ 团队能力
  不要为了技术先进性选择超出团队能力的方案
```

### 常见选型 FAQ

```text
Q1：我们的系统已经有 RAG 了，还需要加 Agent 吗？

A：看数据。
  统计用户请求中，有多少是“单次问答”（RAG 能处理），
  有多少是“多步操作”（需要 Agent）。
  如果多步操作 < 10%，暂时不需要。
  如果 > 30%，值得投入。

Q2：Workflow 和 Agent 的边界在哪？

A：一个简单判断：
  你能画出完整的流程图吗？
  能 → Workflow
  不能（因为分支太多、或取决于中间结果）→ Agent

Q3：能不能在 Workflow 里嵌套 Agent？

A：可以，而且很常见。
  例如：文档处理 Workflow 的第 3 步是“智能分类”，
  这一步用 Agent（因为分类逻辑复杂）。
  其他步骤仍然是确定性的。
  这叫“Workflow + Agent 混合”。

Q4：成本怎么估算？

A：简单公式：
  API：$0（不算服务器）
  RAG：每次 ~$0.01（1 次 LLM 调用）
  Workflow：$0.01-0.1（取决于 LLM 步骤数）
  Agent：$0.05-0.5（取决于步数）

  月成本 = 日请求量 × 30 × 单次成本
  例：1000 次/天 × 30 × $0.1 = $3000/月

Q5：如何向团队推广混合架构？

A：不要一次性推广。
  第 1 步：先加路由层（1 天工作量）
  第 2 步：收集 1 周数据（看请求分布）
  第 3 步：用数据说服团队（"30% 的请求需要 Agent"）
  第 4 步：先做一个场景的 Agent（小范围验证）
  第 5 步：成功后再扩展
```

### 本篇核心要点

```text
1. 四种形态：API < RAG < Workflow < Agent，复杂度递增。
2. 选型原则：用最简单的能解决问题的。
3. 决策树：需要 LLM？需要多步？步骤固定？需要动态决策？
4. 实际系统是混合的：路由层分发到不同处理器。
5. 架构复杂度不能超过团队能力。
6. 从简单开始，用数据驱动演进。
```

## 快速决策清单

