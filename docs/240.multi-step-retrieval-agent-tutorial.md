## 是什么：多步检索到底在做什么

在上一篇中，我们了解了 Query Planning——它把一个复杂问题拆成多个子查询，然后并行执行。这种方式对于"子问题互不依赖"的场景非常有效。比如"对比 A 和 B 的定价"——A 的定价和 B 的定价互不依赖，可以同时搜索。但有一类问题，Query Planning 处理不了：后续查询的内容取决于前一步的结果。

这类问题在企业场景中非常常见。"为什么我的权限变了"需要先查"当前权限是什么"，然后才能查"权限变更规则"。"新政策对项目的影响"需要先查"项目用了哪些流程"，然后才能查"对应流程的新政策"。"账单为什么变高了"需要先查"账单明细"，然后才能查"哪项费用增加了"。这些问题的共同特征是：你不知道第二步应该查什么，直到第一步的结果出来。

### 从一个直觉开始

假设你是一个侦探，正在调查一起商业纠纷。你的任务是搞清楚"新政策对 Atlas 项目有什么影响"。你会怎么做？

如果你是一个"并行搜索员"，你会在没有任何线索的情况下，同时派五个警察去五个不同的地方搜查。但你根本不知道 Atlas 项目涉及哪些流程——你只能猜。你可能猜对了"采购流程"和"审批流程"，但也可能猜了"报销流程"和"人事流程"——而 Atlas 根本不用这些。更糟糕的是，你可能漏掉了真正重要的"合规流程"。

但如果你是一个"侦探"，你会做完全不同的事情。你会先审问嫌疑人（第一步检索），得到线索："Atlas 使用采购流程和审批流程"。然后根据这个线索，你决定下一步去哪里搜查——去查"采购流程的新政策"和"审批流程的新政策"。你不会去查"报销流程的新政策"，因为线索告诉你 Atlas 不用报销流程。

多步检索做的就是"侦探"的工作，而不是"并行搜索员"的工作。它的核心特征是：后一步的查询内容由前一步的证据决定。不是"一开始就决定好所有查询"，而是"走一步看一步，每一步都基于已有证据"。

这个特征让多步检索和"固定管道"有了本质区别。固定管道是"不管情况如何，都执行相同的步骤"——就像工厂流水线，每个产品都经过相同的工序。多步检索是"根据当前情况决定下一步"——就像一个经验丰富的工匠，根据材料的实际情况调整工艺。前者可预测但僵硬，后者灵活但需要"判断力"。多步检索的"判断力"来自模型——这也是为什么它需要更多的安全机制（去重、饱和检测、预算限制）来约束模型的判断。

这个类比揭示了一个重要的认知：多步检索的价值不在于"搜更多次"，而在于"每一步都更精准"。并行搜索是"广撒网"——可能捞到鱼，也可能捞到垃圾。多步检索是"精准钓鱼"——先观察水面（第一步），然后根据观察结果选择钓点（后续步骤）。前者浪费资源在无关方向上，后者把资源集中在有证据支持的方向上。

我想强调一个初学者容易产生的误解：以为多步检索就是"串行版的并行检索"。不是的。并行检索是"同时搜 N 个方向"，多步检索是"根据上一步的结果决定下一步搜什么"。区别不在于"串行还是并行"，而在于"后续查询是否依赖前一步的结果"。如果后续查询不依赖前一步（比如"A 的定价"和"B 的定价"），那就应该并行，不需要多步。只有当后续查询依赖前一步时（比如"先查 Atlas 用什么流程，再查对应政策"），才需要多步。

### 多步检索的定义

有了上面的直觉，我们可以给出一个更精确的定义。多步检索（Multi-Step Retrieval）是 Agentic RAG 中的一种检索策略，它通过迭代循环执行检索：每一步根据当前已收集的证据和未解决的子问题，决定下一步的查询内容。循环持续进行，直到所有子问题都被解决、证据达到饱和、或者检索预算用完。

这里有一个初学者容易混淆的概念：多步检索和 Query Planning 有什么区别？Query Planning 是"一次性规划"——在执行任何检索之前，就把所有子查询都规划好。多步检索是"渐进式规划"——只规划下一步，执行后再规划下下一步。前者适合"子问题互不依赖"的场景，后者适合"子问题有依赖关系"的场景。

用一个更直观的类比来理解这个区别。Query Planning 像是"出发前就规划好完整行程"——第一天去海滩，第二天去博物馆，第三天去美食街。多步检索像是"边走边问路"——先走到路口，问路人"哪条路去海滩"，到了海滩后再问"附近有什么博物馆"。前者效率高（不需要中途问路），但灵活性差（如果海滩关门了，整个计划就废了）。后者效率低（每步都要问路），但灵活性强（可以根据实际情况调整方向）。

### 状态驱动：多步检索的核心机制

多步检索的核心是"状态"。每一步都在状态上追加信息，下一步根据状态决策。这个状态包含四个关键要素。

第一个要素是任务目标（task）。这是用户的原始问题，比如"新政策对 Atlas 项目有什么影响"。任务目标在整个多步检索过程中不变——它是"北极星"，所有步骤都朝着这个方向前进。

第二个要素是已收集证据（evidence）。这是到目前为止所有检索步骤收集到的证据集合。每一步执行后，新证据被追加到这个集合中。下一步的查询规划会参考这些证据——既用来提取"已确认的实体"（比如"Atlas 使用采购流程"），也用来避免重复检索（"这个方向已经搜过了"）。

第三个要素是未解决问题（unresolved）。这是到目前为止还没有被证据回答的子问题列表。初始时，它可能只有一个问题（"Atlas 项目使用哪些流程？"）。随着检索的进行，一些问题被解决（从列表中移除），同时可能产生新的问题（"采购流程的新政策是什么？"被加入列表）。当这个列表为空时，检索完成。

第四个要素是检索预算（budget）。这是系统允许的最大检索次数。多步检索不能无限进行——每一步都有成本（模型调用 + 向量检索），必须有上限。典型预算是 3-5 次。当预算用完时，即使还有未解决问题，也必须停止——然后告诉用户"现有证据不足以完整回答"。

这四个要素之间的关系是这样的：task 决定"方向"，evidence 决定"已知什么"，unresolved 决定"还缺什么"，budget 决定"还能搜几次"。下一步的查询 = f(task, evidence, unresolved, budget)。这个函数就是多步检索的"大脑"——它根据当前状态决定"下一步做什么"。

用一个更直观的类比来理解这四个要素。假设你在玩一个寻宝游戏。task 是"找到宝藏"，evidence 是"你已经找到的线索"（比如"宝藏在北边"），unresolved 是"你还没搞清楚的"（比如"北边的哪个位置"），budget 是"你还能挖几次"。每一步，你根据已有线索决定下一步挖哪里。挖到新线索后，更新你的认知，再决定下一步。这就是多步检索的工作方式。

### 什么时候需要多步检索

并不是所有问题都需要多步检索。这是一个重要的认知——多步检索有成本（多次模型调用、串行延迟），如果问题可以一步解决，多步只会增加延迟。

判断标准是：后续查询的内容是否取决于前一步的结果？如果后续查询不依赖前一步（比如"A 的定价"和"B 的定价"），那就用并行检索（Query Planning）。如果后续查询依赖前一步（比如"先查 Atlas 用什么流程，再查对应政策"），那就用多步检索。

这个判断本身也可以自动化。在实践中，你可以用一个简单的启发式：如果用户的问题中包含"影响""导致""为什么""结果"等因果词，通常意味着有依赖关系——因为"影响"需要先知道"被影响的对象是什么"，然后才能查"影响是什么"。相反，如果问题中包含"对比""区别""和""与"等并列词，通常意味着无依赖——因为"对比 A 和 B"可以拆成独立的"A 是什么"和"B 是什么"。

我想强调一个初学者容易犯的错误：过度使用多步检索。有些开发者觉得"多步检索这么强大，所有问题都走多步不就行了？"这是不对的。对于简单问题（"年假政策是什么"），一步检索就够了，多步只会把 200ms 的延迟变成 600ms。对于可以并行的问题（"对比 A 和 B"），多步会把并行变成串行，延迟翻倍。多步检索的价值在于"解决有依赖关系的复杂问题"，而不是"替代所有检索策略"。

工程的核心是"在正确的地方花正确的成本"。多步检索的成本是延迟（串行等待）和复杂度（状态管理、去重、饱和检测）。如果问题不需要这种复杂度，就不要强加它。判断"是否需要多步"本身就是一个重要的工程决策——这个决策做错了，要么浪费时间（不需要多步但用了多步），要么丢失信息（需要多步但用了单步）。

## 为什么：不做多步会出什么问题

理解了多步检索是什么之后，你可能会问："直接用 Query Planning 不就行了？为什么非要多步？"答案是：对于有依赖关系的问题，Query Planning 会导致三个严重的问题。

### 问题一：盲目猜测导致资源浪费

Query Planning 在执行任何检索之前就生成所有子查询。但对于有依赖关系的问题，后续查询的内容取决于前一步的结果——在第一步执行之前，你根本不知道后续应该查什么。

比如"新政策对 Atlas 项目有什么影响"。如果你用 Query Planning，它必须在没有任何证据的情况下猜测 Atlas 项目涉及哪些流程。它可能猜"采购流程""审批流程""报销流程""人事流程"——但 Atlas 实际上只用"采购流程"和"审批流程"。结果就是：四次检索中有两次是浪费的（报销和人事），而且可能漏掉了真正重要的流程。

这种浪费不只是"多花了点时间"的问题。在企业场景中，每一次检索都有成本——向量数据库的查询费用、模型的调用费用、网络延迟。如果你的系统每天处理 1 万个问题，每个问题浪费 2 次检索，就是每天 2 万次无效调用。按月累计，这是一笔不小的开支。更重要的是，无效检索占用了预算——如果预算是 4 次，浪费了 2 次在无关方向上，只剩 2 次给真正重要的方向。

为什么模型会猜错？因为模型没有"事实知识"——它不知道你的企业中 Atlas 项目具体用了哪些流程。它只能根据训练数据中的"常见项目流程"来猜测。但每个企业的项目都是独特的——你的 Atlas 可能只用两个流程，也可能用七个流程。这种"企业特定知识"只有你的数据源里才有，模型猜不到。

用一个更直观的类比来理解。假设你要调查"新交通法规对张三有什么影响"。如果你不知道张三有什么车，你只能猜："张三可能有轿车、卡车、摩托车、电动车"。然后你分别去查每种车的新法规。但如果张三只有一辆轿车，你查卡车、摩托车和电动车的时间就全浪费了。正确的做法是：先查"张三有什么车"（第一步），得到"轿车"后，再查"轿车的新交通法规"（第二步）。这就是多步检索的价值——用证据替代猜测。

### 问题二：遗漏关键信息

盲目猜测不仅浪费资源，还会遗漏关键信息。模型的"常识"可能不包含你企业中的特殊情况。比如 Atlas 项目可能使用了一个非常规的"合规审查流程"——这在大多数企业中不常见，模型不太可能猜到。但对于"新政策的影响"这个问题，合规审查流程可能是受影响最大的。

如果你用 Query Planning，模型大概率不会生成"合规审查流程的新政策"这个查询——因为它不知道 Atlas 有这个流程。但如果你用多步检索，第一步"Atlas 使用哪些流程"的证据中会包含"合规审查流程"，然后第二步自然会去查"合规审查流程的新政策"。

这种"遗漏"比"浪费"更危险。浪费只是多花了时间和资源，遗漏意味着答案不完整——用户得到的答案缺少了关键信息，但他不知道缺少了。他以为"新政策只影响采购和审批"，实际上还影响了合规审查。这种"不知道自己不知道"的状态是最危险的。

在企业场景中，这种"遗漏"可能导致严重的业务后果。比如，用户基于不完整的答案做了一个业务决策（"新政策只影响采购流程，所以我只要调整采购流程就行了"），但实际上合规审查流程也受到了影响。结果就是：用户以为自已已经合规了，但实际上还有一个流程没有调整。这种"假合规"比"明确不合规"更危险——因为前者不会被发现，直到审计时纔暴露。

### 问题三：无法处理链式依赖

有些问题的依赖关系不是"一层"的，而是"多层"的。比如"为什么我的账单比上月高"。第一步：查账单明细，发现"API 调用费增加了"。第二步：查 API 调用记录，发现"调用量从 1 万增加到 5 万"。第三步：查调用量增加的原因，发现"新上线的功能触发了大量调用"。

这种链式依赖（A → B → C）是 Query Planning 完全无法处理的。因为第二步的查询内容（"API 调用记录"）取决于第一步的结果（"API 调用费增加了"），第三步的查询内容（"调用量增加的原因"）取决于第二步的结果（"调用量从 1 万增加到 5 万"）。在第一步执行之前，你根本不知道第二步应该查什么。

我想特别强调"链式依赖"和"扇形依赖"的区别。扇形依赖是"一步的结果扇出为多个并行查询"——比如"Atlas 用采购和审批两个流程"扇出为"查采购政策"和"查审批政策"，这两个可以并行。链式依赖是"一步的结果是下一步的输入"——比如"账单高了"→"API 费增加了"→"调用量增加了"→"新功能上线了"，每一步都必须等前一步完成。在实际问题中，这两种依赖经常混合出现——先链式走几步，然后某一步扇出为并行。好的多步检索实现应该能处理这种混合结构。

用一个更直观的类比来理解。假设你去看医生，说"我头疼"。医生不会在没有任何检查的情况下就开药。他会先量体温（第一步），发现发烧了。然后根据"发烧"这个线索，安排血常规检查（第二步），发现白细胞偏高。然后根据"白细胞偏高"这个线索，判断是细菌感染（第三步），最后开抗生素。每一步的检查都取决于上一步的结果。如果医生在你说"我头疼"的时候就同时开了体温计、血常规、CT、X 光、心电图——这就是"并行搜索"，浪费了大量资源在可能不需要的检查上。

### 问题四：答案缺乏可解释性

当系统用并行搜索一次性生成所有查询时，最终答案的引用是"平坦"的——"来源：文档 A、文档 B、文档 C"。用户不知道"为什么系统会去查这些文档"。但多步检索的引用是"链式"的——"这个结论来自第 2 步的采购文档，第 2 步是因为第 1 步发现 Atlas 用了采购流程"。这种链式引用让用户能理解"系统的推理过程"，显著提升信任感。

为什么可解释性在企业场景中特别重要？因为企业用户往往不是"普通用户"，而是"专家用户"——他们需要验证答案的正确性，而不是盲目接受。当专家用户看到"系统先查了 Atlas 的流程，发现用了采购流程，然后去查了采购新政策"时，他能判断"这个推理过程是合理的"。但如果他只看到"来源：采购政策文档"，他不知道"系统为什么去查这个文档"——可能是巧合，也可能是正确的推理。链式引用让"巧合"和"推理"变得可区分。

## 怎么做：工程实现

理解了多步检索的价值之后，让我们看看如何在工程中实现它。我会按照"数据结构 → 决策逻辑 → 主循环 → 安全机制"的顺序展开。这个顺序不是随意的——数据结构决定了"能记录什么"，决策逻辑决定了"每一步做什么"，主循环把两者串起来，安全机制保证不会失控。

### 检索步骤的数据结构

首先，我们需要一个数据结构来记录每一步的检索。这个记录不仅包含"查了什么"和"找到了什么"，还包含"这一步依赖哪一步"——这个依赖关系对于后续的调试和可解释性至关重要。

```python
from dataclasses import dataclass, field
from pydantic import BaseModel


@dataclass
class RetrievalStep:
    """
    一次检索步骤的完整记录。

    设计要点：
    - depends_on 记录依赖关系，形成 DAG（有向无环图）
    - evidence_ids 记录这一步产生了哪些证据
    - unresolved_after 记录这一步执行后还有哪些问题没解决
    """
    query_id: str                          # 查询唯一标识
    query: str                             # 实际查询文本
    source: str                            # 目标数据源
    depends_on: list[str]                  # 依赖的前序 query_id
    evidence_ids: list[str] = field(default_factory=list)
    unresolved_after: list[str] = field(default_factory=list)
    latency_ms: int = 0                    # 这一步的耗时


@dataclass
class Evidence:
    """一条检索到的证据。"""
    evidence_id: str
    text: str
    source: str
    version: str | None = None
    effective_date: str | None = None


class MultiStepState(BaseModel):
    """
    多步检索的全局状态。

    每一步都读取和修改这个状态。
    状态的完整性决定了系统的可观测性——
    如果状态记录不完整，Bad Case 调试就无法进行。
    """
    task: str                              # 用户原始问题
    evidence: list[Evidence] = []          # 已收集的证据
    unresolved_questions: list[str] = []   # 未解决的子问题
    steps: list[RetrievalStep] = []        # 已执行的步骤
    retrieval_calls: int = 0               # 已检索次数
    max_retrieval_calls: int = 4           # 检索预算
    stop_reason: str | None = None         # 停止原因
```

为什么状态中要记录 `steps` 而不只是 `evidence`？因为 `evidence` 只告诉你"找到了什么"，不告诉你"怎么找到的"。当答案出错时，你需要回放每一步的决策过程：第一步查了什么、为什么查这个、找到了什么、为什么决定第二步查那个。没有 `steps`，你只能看到最终的证据集合，无法判断"是哪一步出了问题"。这就像看一场足球比赛的最终比分——你知道谁赢了，但不知道"是怎么赢的"。如果你要改进战术，你需要看每一步的传球和跑位，而不只看比分。

### 下一步查询的决策逻辑

多步检索的核心是"下一步查什么"的决策函数。这个函数接收当前状态，输出下一步的查询（或者 None 表示停止）。

```python
def next_query(state: MultiStepState) -> str | None:
    """
    决定下一步查询。

    停止条件（返回 None）：
    1. 预算用完——不能无限检索
    2. 没有未解决问题——所有子问题都已解决
    3. 已有停止原因——之前已经决定停止了

    否则：根据已有证据和未解决问题，规划下一步。
    """
    # 停止条件检查
    if state.stop_reason:
        return None
    if state.retrieval_calls >= state.max_retrieval_calls:
        state.stop_reason = "budget_exhausted"
        return None
    if not state.unresolved_questions:
        state.stop_reason = "all_resolved"
        return None

    # 从已有证据中提取已确认的实体
    confirmed_entities = extract_entities(state.evidence)

    # 规划下一步（只能基于已确认实体，不能凭空猜测）
    query = plan_next(
        task=state.task,
        confirmed_entities=confirmed_entities,
        unresolved=state.unresolved_questions,
        existing_queries=[s.query for s in state.steps],
    )
    return query


def extract_entities(evidence: list[Evidence]) -> set[str]:
    """
    从已有证据中提取已确认的实体。

    关键原则：只有证据中明确提到的实体才能用于后续查询。
    模型"猜测"的实体不算——必须有证据支持。
    """
    entities = set()
    for e in evidence:
        # 实际实现中可以用 NER 或规则提取
        # 这里简化为从文本中提取关键名词
        entities.update(extract_nouns(e.text))
    return entities


def plan_next(
    task: str,
    confirmed_entities: set[str],
    unresolved: list[str],
    existing_queries: list[str],
) -> str:
    """
    调用模型规划下一步查询。

    Prompt 中的关键约束：
    1. 只能使用 confirmed_entities 中的实体
    2. 必须针对 unresolved 中的某个问题
    3. 不能与 existing_queries 重复
    """
    prompt = f"""你是一个检索规划器。根据当前状态决定下一步查询。

任务目标：{task}
已确认实体：{confirmed_entities}
未解决问题：{unresolved}
已执行查询：{existing_queries}

约束：
- 只能使用"已确认实体"中出现的实体（不能猜测）
- 必须针对"未解决问题"中的某一个
- 不能与"已执行查询"重复
- 输出一个简洁的检索查询

下一步查询："""
    return llm_generate(prompt)
```

为什么"只能使用已确认实体"这个约束如此重要？因为模型的"想象力"在这里是危险的。如果模型在第一步证据中看到了"Atlas 使用采购流程"，它可能"联想"到"Atlas 可能还使用报销流程"——但这个联想没有任何证据支持。如果允许模型使用"猜测的实体"，后续查询就会偏离事实基础，变成"基于幻觉的检索"。这不仅浪费预算，还可能返回完全无关的结果。

### Prompt 设计要点

多步检索中 Planner 的 prompt 设计有几个关键要点，值得单独讨论。

第一个要点：明确告诉模型"你的角色是规划下一步查询，不是回答问题"。如果不明确这个角色，模型可能会"顺便"回答用户的问题——而不是生成查询。比如用户问"新政策对 Atlas 的影响"，模型可能直接输出"新政策要求采购超过 5 万需要总监审批"——这是答案，不是查询。正确的输出应该是"采购流程最新政策条款"——这是一个查询。在 prompt 中明确"输出一个检索查询，不要输出答案"能避免这个问题。

第二个要点：把"已确认实体"以明确的列表形式提供，而不是嵌入在一段文本中。比如"已确认实体：[Atlas, 采购流程, 审批流程]"比"根据证据，Atlas 项目使用了采购流程和审批流程"更清晰。模型对结构化输入的遵守度比非结构化输入高得多——当实体以列表形式出现时，模型更不容易"超出列表范围"。

第三个要点：把"已执行查询"也列出来，让模型知道"什么已经搜过了"。如果不提供这个信息，模型可能生成一个和之前完全相同的查询——因为它不知道这个查询已经执行过了。列出已执行查询能让模型主动避免重复，而不是完全依赖后端的 fingerprint 去重。

第四个要点：限制输出长度。查询应该是一个简洁的句子（10-20 字），而不是一段话。如果模型输出了一段话作为查询，向量检索的效果会很差——因为向量模型对短查询的编码质量比长文本高。在 prompt 中加上"输出不超过 20 个字"能有效控制查询长度。

这四个要点看起来都是"小细节"，但它们对 Planner 的输出质量影响很大。在实践中，我发现 prompt 的"结构化程度"和"约束明确性"是决定 Planner 质量的两个最重要因素。一个结构清晰、约束明确的 prompt，比一个"写得很漂亮但约束模糊"的 prompt 效果好得多。

### 主循环：多步检索的执行引擎

有了决策函数，我们可以构建多步检索的主循环。这个循环是多步检索的"引擎"——它反复执行"决策 → 检索 → 更新状态"，直到满足停止条件。

```python
def multi_step_retrieve(
    task: str,
    initial_question: str,
    max_calls: int = 4,
) -> MultiStepState:
    """
    多步检索主循环。

    流程：
    1. 初始化状态（设置任务、初始问题、预算）
    2. 循环：决策 → 去重检查 → 检索 → 饱和检测 → 更新状态
    3. 停止后返回最终状态

    返回的 state 包含完整的步骤记录和证据集合。
    """
    state = MultiStepState(
        task=task,
        unresolved_questions=[initial_question],
        max_retrieval_calls=max_calls,
    )

    saturation_count = 0
    executed_fingerprints: set[str] = set()

    while True:
        # 决策：下一步查什么
        query = next_query(state)
        if query is None:
            break

        # 去重：是否已经执行过相同的检索
        fp = retrieval_fingerprint(query)
        if fp in executed_fingerprints:
            # 跳过重复查询，从 unresolved 中移除对应问题
            state.unresolved_questions.pop(0)
            continue
        executed_fingerprints.add(fp)

        # 执行检索
        new_evidence = retrieval_tool.retrieve(query)

        # 饱和检测：新证据是否带来了新信息
        if check_saturation(new_evidence, state.evidence):
            saturation_count += 1
            if saturation_count >= 2:
                state.stop_reason = "evidence_saturation"
                break
        else:
            saturation_count = 0

        # 更新状态
        state.evidence.extend(new_evidence)
        state.retrieval_calls += 1
        step = RetrievalStep(
            query_id=f"q-{state.retrieval_calls}",
            query=query,
            source="auto",
            depends_on=[s.query_id for s in state.steps[-1:]],
            evidence_ids=[e.evidence_id for e in new_evidence],
        )
        state.steps.append(step)

        # 更新未解决问题（由模型判断哪些已解决、哪些新增）
        state.unresolved_questions = update_unresolved(
            task=state.task,
            evidence=state.evidence,
            current_unresolved=state.unresolved_questions,
        )

    return state
```

这里有一个值得深入讨论的设计决策：`update_unresolved` 是由模型来判断的，而不是由规则判断的。为什么？因为"某个子问题是否已被解决"这个判断需要语义理解——不能用简单的关键词匹配。比如，unresolved 中有"采购流程的新政策是什么"，而新证据是"根据 2024 年版采购管理办法，超过 5 万元的采购需要总监审批"——这条证据是否解决了"采购流程的新政策是什么"？需要模型来判断。

但模型判断也有风险：模型可能"过于乐观"地认为问题已解决（实际上证据不充分），或者"过于保守"地认为问题未解决（实际上证据已经充分）。在实践中，我建议加一个"置信度阈值"：只有当模型以高置信度（> 0.8）判断"已解决"时，才从 unresolved 中移除。低置信度的判断保持 unresolved 状态，让后续步骤继续补充证据。

这个主循环中有三个关键的"安全阀"：去重检查、饱和检测和预算限制。去重检查防止"用不同的措辞搜同一个东西"。饱和检测防止"在搜不到新东西的情况下反复浪费预算"。预算限制防止"无限循环"。这三个安全阀缺一不可——没有去重，模型可能反复搜同一个方向；没有饱和检测，模型可能在"搜不到"的情况下反复尝试；没有预算限制，模型可能永远不停。

用一个类比来理解这三个安全阀。假设你派一个实习生去图书馆查资料。去重检查相当于"你已经借过这本书了，不要再借一次"。饱和检测相当于"你连续两次去同一个楼层都没找到新资料，说明这个楼层已经搜尽了"。预算限制相当于"你最多只能去四次图书馆，不管找没找到都要回来"。没有这三个约束，实习生可能在图书馆里转一整天，借了四本相同的书，或者永远不回来。

### 去重机制

去重是多步检索中特别重要的一个机制。因为模型在不同步骤中可能生成"措辞不同但含义相同"的查询。比如第一步搜了"Atlas 项目使用哪些流程"，第三步可能又生成"Atlas 项目的业务流程有哪些"——措辞不同，但会返回相同的结果。

```python
import hashlib
import re


def retrieval_fingerprint(query: str) -> str:
    """
    生成检索指纹：用于判断是否已经执行过相同的检索。

    标准化步骤：
    1. 转小写
    2. 去除标点符号
    3. 去除停用词（的、了、是、在、有...）
    4. 排序剩余词（消除语序差异）
    5. 取 hash

    这样 "Atlas 项目使用哪些流程" 和 "Atlas 项目的业务流程有哪些"
    标准化后都变成 "atlas 项目 流程 业务"（排序后相同），
    生成相同的 fingerprint。
    """
    # 转小写
    text = query.lower()
    # 去除标点
    text = re.sub(r'[^\w\s]', '', text)
    # 去除停用词
    stop_words = {'的', '了', '是', '在', '有', '哪些', '什么', '哪个'}
    words = [w for w in text.split() if w not in stop_words]
    # 排序（消除语序差异）
    words.sort()
    # 取 hash
    canonical = ' '.join(words)
    return hashlib.md5(canonical.encode()).hexdigest()


# 使用示例
fp1 = retrieval_fingerprint("Atlas 项目使用哪些流程")
fp2 = retrieval_fingerprint("Atlas 项目的业务流程有哪些")
# fp1 == fp2 → 被去重拦截
```

但去重也有局限性。如果模型用完全不同的语言生成查询（比如中文 vs 英文），fingerprint 就不同了。"Atlas 项目流程"和"Atlas project workflows"会生成不同的 fingerprint，绕过去重。在实践中，如果你的数据源是多语言的，可能需要跨语言去重——先用翻译模型统一语言，再做 fingerprint。但这增加了复杂度和延迟，只有在多语言场景中才值得做。

### 证据饱和检测

饱和检测解决的是"搜不到新东西但还在反复搜"的问题。如果连续两轮检索返回的证据都是已有证据的重复，说明"这个方向已经搜尽了"——继续搜也不会有新信息。

```python
def check_saturation(
    new_evidence: list[Evidence],
    existing_evidence: list[Evidence],
) -> bool:
    """
    检测证据是否饱和。

    饱和定义：新增证据全部与已有内容重复（没有新信息）。
    如果连续两轮饱和，停止检索。

    为什么用"连续两轮"而不是"一轮"？
    因为一轮饱和可能是偶然（比如这一步的查询措辞不好），
    连续两轮饱和才说明"真的搜不到新东西了"。
    """
    existing_texts = {e.text for e in existing_evidence}
    new_unique = [e for e in new_evidence if e.text not in existing_texts]
    return len(new_unique) == 0
```

为什么阈值是"连续两轮"而不是"一轮"？因为单轮饱和可能是偶然的——也许这一步的查询措辞不太好，导致返回了重复结果，但换一个措辞可能就有新结果了。连续两轮饱和才说明"这个方向确实搜尽了"，不是措辞问题。这个阈值可以根据实际效果调整——如果你的数据源比较小（文档数量有限），一轮饱和就足够了；如果数据源很大，可能需要三轮。

### 证据冲突处理

多步检索中，不同步骤可能返回相互矛盾的证据。比如第一步从旧版文档中检索到"采购上限 10 万"，第二步从新版文档中检索到"采购上限 5 万"。系统必须处理这种冲突——不能简单地"取最后一个"或"取相似度最高的"。

```python
def resolve_conflict(evidence_a: Evidence, evidence_b: Evidence) -> dict:
    """
    处理证据冲突。

    处理原则（按优先级）：
    1. 按版本号判断（version 大的优先）
    2. 按生效日期判断（effective_date 新的优先）
    3. 无法判断时，披露冲突（让用户知道有矛盾）

    关键设计：绝不自动"猜"哪个对。
    相似度 ≠ 正确性。一条证据和查询更相似，
    不代表它更正确——可能只是措辞更接近。
    """
    # 尝试按版本判断
    if evidence_a.version and evidence_b.version:
        newer = max(evidence_a, evidence_b, key=lambda e: e.version)
        return {"resolution": "version", "winner": newer.evidence_id}

    # 尝试按日期判断
    if evidence_a.effective_date and evidence_b.effective_date:
        newer = max(evidence_a, evidence_b, key=lambda e: e.effective_date)
        return {"resolution": "date", "winner": newer.evidence_id}

    # 无法判断：披露冲突
    return {
        "resolution": "conflict_disclosed",
        "evidence_a": evidence_a.evidence_id,
        "evidence_b": evidence_b.evidence_id,
        "message": "存在冲突证据，无法自动判断哪个有效",
    }
```

为什么"披露冲突"比"自动选择"更安全？因为在企业场景中，错误的自动选择可能导致严重的业务后果。如果系统自动选择了"采购上限 10 万"（旧版），而实际有效的是"采购上限 5 万"（新版），用户可能基于错误的信息发起一笔 8 万的采购——然后被合规部门拒绝。但如果系统披露了冲突（"存在两个版本的政策，请确认哪个有效"），用户就能做出正确判断。

在实践中，冲突披露的展示方式也很重要。不要只是说"存在冲突"——要具体说明"哪两条证据冲突、冲突的内容是什么、各自的版本/日期是什么"。这样用户才能做出明智的判断。比如："证据 A（2023 年版）说采购上限 10 万，证据 B（2024 年版）说采购上限 5 万。请确认当前有效的是哪个版本。"这比"存在冲突证据"有用得多。

还有一个值得注意的场景："部分冲突"。两条证据不是完全矛盾，而是在某个细节上不一致。比如证据 A 说"采购超过 5 万需要总监审批"，证据 B 说"采购超过 5 万需要副总裁审批"。这不是"完全冲突"（两条都说了"超过 5 万需要审批"），但在"谁来审批"这个细节上不一致。对于部分冲突，可以"取共同部分 + 披露差异部分"——答案中写"采购超过 5 万需要高级审批"，然后注明"具体审批人存在不同版本的说法"。

### 完整运行示例

让我们把上面的组件组合起来，看一个完整的运行过程。

```python
for step in result.steps:
    print(f"  Step {step.query_id}: '{step.query}' → {len(step.evidence_ids)} 条证据")
# → Step q-1: 'Atlas 项目使用哪些业务流程？' → 2 条证据
# → Step q-2: '采购流程最新政策条款' → 2 条证据
# → Step q-3: '审批流程最新政策条款' → 1 条证据

print(f"未解决问题: {result.unresolved_questions}")
# → []（全部解决）
```

注意这个执行过程：第一步查"Atlas 用什么流程"，得到"采购流程和审批流程"。第二步和第三步分别查"采购流程的新政策"和"审批流程的新政策"——这两个查询的内容完全取决于第一步的结果。如果第一步的结果是"Atlas 使用合规审查流程"，那第二步就会变成"合规审查流程的新政策"。这就是"后一步依赖前一步"的含义。

我想请你特别注意这个例子中的一个细节：第二步和第三步互不依赖（都只依赖第一步的结果），所以它们可以并行执行。这意味着多步检索不一定是"完全串行"的——它可以是"层内并行、层间串行"的。第一步是"探索层"（搞清楚基本情况），第二步是"深入层"（针对每个方向深入查询）。探索层只有一步，深入层可以有多步并行。这种"先探索后深入"的模式是多步检索最常见的结构。

还有一个值得注意的设计决策：`initial_question` 是"Atlas 项目使用哪些业务流程？"而不是用户的原始问题"新政策对 Atlas 项目有什么影响？"。为什么？因为用户的原始问题太宽泛，不适合直接作为检索查询。第一步应该是一个"探索性查询"——它的目标不是直接回答问题，而是为后续步骤提供方向。这种"先探索后深入"的策略是多步检索的核心模式。

### 实战案例：SaaS 客服系统

让我们看一个更贴近实际的案例。假设你在为一个 SaaS 平台构建客服 Agent，用户问："为什么我的高级报表功能突然不能用了？"

这个问题看起来简单，但实际上包含多层依赖。第一步：查用户当前的套餐等级（需要调用业务 API，不是文档检索）。假设得到"专业版"。第二步：查"专业版是否支持高级报表"（文档检索）。假设得到"专业版不包含高级报表，需要企业版"。第三步：查"该用户最近的套餐变更记录"（审计日志检索）。假设得到"上周从企业版降级为专业版"。

注意这个过程中的依赖关系：第二步的查询内容（"专业版是否支持高级报表"）取决于第一步的结果（"专业版"）。如果第一步的结果是"企业版"，第二步就会变成"企业版的高级报表权限配置"——完全不同的方向。第三步的查询内容（"套餐变更记录"）取决于第二步的结果（"专业版不支持"）——如果第二步的结果是"专业版支持高级报表"，就不需要查套餐变更了，而是应该查"功能配置是否被手动关闭"。

这个案例还展示了一个重要的工程决策：第一步不是文档检索，而是 API 调用。这意味着多步检索的"检索"不应该局限于"向量数据库搜索"——它可以是任何形式的"信息获取"。在 Tool-Augmented RAG（下一篇的主题）中，我们会把这个思想推广到极致。

### 测试策略

多步检索的测试比单步检索更复杂，因为你不仅要测试"最终答案对不对"，还要测试"每一步的决策对不对"。我建议分四层测试。

第一层：结构合法性测试。检查每一步的输出是否符合 schema——query_id 是否存在、depends_on 是否指向已执行的步骤、evidence_ids 是否非空。这是最基本的测试，可以用单元测试覆盖。

第二层：决策质量测试。给定一个固定的状态（固定的 evidence 和 unresolved），检查 Planner 生成的下一步查询是否合理。比如，如果 evidence 说"Atlas 用采购和审批流程"，unresolved 是["采购流程的新政策", "审批流程的新政策"]，那 Planner 应该生成"采购流程新政策条款"或"审批流程新政策条款"，而不是"Atlas 的预算是多少"。这种测试可以用"固定输入 + 期望输出"的方式写。

第三层：端到端回归测试。准备一组"问题 + 期望证据集"的测试用例，跑完整的多步检索流程，检查最终收集到的证据是否覆盖了期望集。这种测试能发现"单步测试发现不了的问题"——比如"第一步正确但第二步决策错误"。

第四层：边界条件测试。测试预算用完时的行为（应该停止并报告不足）、测试数据源不可用时的行为（应该降级）、测试所有查询都被去重拦截时的行为（应该停止并报告饱和）。这些边界条件是生产环境中最容易出问题的地方。

## 常见失败模式

理解了正确做法之后，让我们看看实际开发中最常犯的错误。这些失败模式每一个都会导致答案质量下降或资源浪费。理解它们的价值不仅在于"避免犯错"，更在于理解"为什么正确做法是那样的"——很多设计决策正是为了避免这些失败而做出的。

我建议你在阅读这些失败模式时，不要只是"记住不要这样做"，而是思考"为什么开发者会犯这个错误"。大多数失败模式的根源不是"开发者不知道正确做法"，而是"正确做法在短期内看起来更复杂、更慢、更贵"。理解这些权衡能帮你在面对"要不要省这一步"的决策时做出正确选择。

### 所有 query 在开始时一次生成

这是最常见的错误，也是多步检索要解决的核心问题。开发者在第一步之前就生成了所有查询——但后续查询的内容应该取决于第一步的结果。在没有结果的情况下猜测后续查询，就像在没有线索的情况下决定搜查所有地点——浪费且可能遗漏。

为什么开发者会犯这个错误？因为"一次生成所有查询"在实现上更简单——不需要循环、不需要状态管理、不需要饱和检测。但这种简单性是以正确性为代价的。对于有依赖关系的问题，一次生成的查询必然包含猜测——而猜测在企业场景中是不可接受的。

这个失败模式还有一个更隐蔽的变体：开发者确实实现了多步循环，但每一步的查询不是基于上一步的证据，而是基于"原始问题的拆解"。比如第一步查"Atlas 用什么流程"，第二步不是基于第一步的证据（"采购和审批"），而是基于原始问题的拆解（"新政策的采购条款""新政策的审批条款""新政策的报销条款"）。这看起来像多步，但实际上还是"一次生成"——因为后续查询不依赖第一步的结果。真正的多步是：如果第一步说"Atlas 只用采购流程"，那第二步就只查"采购新政策"，不会查"审批新政策"或"报销新政策"。

### 后一步使用模型猜测而非 evidence

模型在规划下一步时，可能"联想"出证据中不存在的实体。比如证据说"Atlas 使用采购流程和审批流程"，模型可能联想到"Atlas 可能还使用人事流程"——然后用"人事流程"去检索。这不仅浪费预算，还可能返回完全无关的结果。

修复方法是在 prompt 中明确约束"只能使用已确认实体"，并在后端校验：如果生成的查询包含证据中不存在的实体，拒绝执行。这种"模型提议 + 后端强制"的模式是整个 Agentic RAG 的核心安全机制。

### 不记录 query → evidence 映射

如果最终答案引用了 ev-005，但你不知道 ev-005 是哪次查询产生的，你就无法判断"检索策略是否有效"。当 Bad Case 发生时，你需要知道"这条证据是哪个查询找到的"，才能判断"是查询写得不好，还是数据源里没有"。

修复方法是每一步都记录 `evidence_ids`——这一步产生了哪些证据。通过 query_id 和 evidence_id 的映射，你可以完整地回放"从查询到证据到答案"的链路。

### 同义改写绕过去重

如果 normalize 不够好，模型可以用不同的措辞绕过 fingerprint 去重。比如"Atlas 项目流程"和"Atlas project workflows"——语义相同但 fingerprint 不同。修复方法是加强 normalize（去停用词、词干化），或者在跨语言场景中先翻译再 fingerprint。

### 证据饱和仍继续检索

如果连续两轮检索返回的证据都是重复的，说明"这个方向已经搜尽了"。继续检索只会浪费预算，不会带来新信息。修复方法是实现饱和检测：连续 N 轮无新信息就停止。

### 达到预算后编造缺失结论

预算用完但还有未解决问题时，模型可能"编造"一个结论来"填补空白"。比如"根据已有信息推测，审批流程可能..."——这是幻觉。正确的做法是明确告诉用户"关于审批流程的新政策，现有资料不足以回答"。承认"不知道"比编造一个"看起来合理"的答案安全得多。

为什么模型会"编造"？因为语言模型的训练目标是"生成连贯的文本"——它被训练为"总是给出答案"，而不是"承认不知道"。这种训练偏见在企业场景中是危险的——用户需要的是"可靠的答案"，而不是"流畅的猜测"。修复方法是在生成答案的 prompt 中明确约束："如果证据不足以回答某个子问题，必须明确说明'现有资料不足'，不得推测。"

### 这些失败模式的共同根源

回顾上面六个失败模式，你会发现它们有一个共同的根源：对"模型自主性"的过度信任。模型想"一次规划所有查询"（失败模式 1）、想"猜测未知实体"（失败模式 2）、想"编造缺失结论"（失败模式 6）——这些都是模型"太有主见"的表现。正确的做法是：模型只负责"在约束内生成查询"，所有"边界判断"（是否停止、是否超预算、是否有冲突）都由确定性代码控制。

## 什么时候不要这么做

### 子问题互不依赖时直接并行

如果用户问"A 的定价和 B 的定价"，两个子问题互不依赖——查 A 不需要先知道 B 的结果。这种情况下，用 Query Planning 并行搜索即可，不需要多步。多步只会把并行变成串行，延迟翻倍，答案质量没有提升。

### 单步检索已经满足时不要多步

如果用户问"年假政策是什么"，一步检索就够了。多步检索会把 200ms 的延迟变成 600ms（三步 × 200ms），但答案质量没有任何提升。判断标准很简单：如果问题只有一个证据目标，且数据源明确，就直接检索。

### 数据源没有版本和时间字段时先补数据治理

如果你的文档没有 version 和 effective_date 字段，证据冲突就无法自动判断。多步检索可能从不同版本的文档中检索到矛盾信息，但无法判断哪个有效。这种情况下，先补数据治理（给文档加版本号和生效日期），再上多步检索。否则，多步检索反而可能让问题更复杂——因为它会从多个版本中拉取信息，增加冲突的概率。

### 这个"不要"背后的思维模式

上面三个"不要"背后有一个共同的思维模式：不要试图用"更复杂的技术"来解决"不需要复杂性"的问题。多步检索的价值在于"处理依赖关系"——如果没有依赖关系，它就是过度工程。工程的核心不是"用最高级的技术"，而是"用最合适的技术"。一把锤子能解决所有钉子问题，但不是所有问题都是钉子。

用一个类比来理解。如果你要去超市买牛奶和面包，你不需要"先查牛奶在哪个货架，到了牛奶货架后再查面包在哪个货架"——因为牛奶和面包的位置互不依赖，你进超市时就可以同时看两个方向。但如果你要"根据今天的食材决定做什么菜，然后根据菜决定还缺什么调料"，这就是依赖关系——你必须先决定做什么菜，才能知道缺什么调料。多步检索解决的是后者，不是前者。

还有一个常见的"不要"场景：当数据源非常小（比如只有 20 篇文档）时，多步检索的价值很小。因为数据源小到"一次检索就能覆盖大部分相关内容"，不需要"逐步深入"。多步检索的价值在大数据源中才能体现——当数据源有上万篇文档时，一次检索很难精确命中所有相关内容，需要"先缩小范围，再精确搜索"。

### 演进路径：从简单到复杂

如果你的系统还没有多步检索，不建议一步到位实现完整版本。我建议按以下路径演进：

第一阶段：先实现"两步检索"。只做一步探索 + 一步深入。比如先查"Atlas 用什么流程"，然后只查第一个结果的对应政策。这很简单，但已经能验证"多步是否有价值"。如果两步检索的答案质量比单步明显提升，说明你的场景确实需要多步。

第二阶段：加上循环和预算。从"固定两步"变成"最多 N 步"。加上预算限制（最多 4 步）和停止条件（unresolved 为空时停止）。这一步不需要去重和饱和检测——先验证"循环多步"的基本价值。

第三阶段：加上去重和饱和检测。当你发现"模型反复搜同一个方向"或"搜不到新东西但还在继续"时，加上去重和饱和检测。这两个机制是"优化"，不是"基础"——没有它们系统也能工作，只是会浪费一些预算。

第四阶段：加上并行优化和冲突处理。当你发现"第二步和第三步可以并行但现在是串行"时，加上层内并行。当你发现"不同步骤返回了矛盾信息"时，加上冲突处理。这些是"锦上添花"的优化，不是"必须有"的基础。

这种演进路径的好处是：每一步都能独立验证价值，不需要"全部做完才能上线"。如果第一步就发现"多步没有价值"，你就不需要继续做第二、三、四步了。这比"一次性做完所有功能然后发现不需要"节省大量时间。

### 路由策略：如何决定走多步还是单步

在实际系统中，不是所有问题都走多步检索。你需要一个"路由器"来决定每个问题走哪条路径。这个路由器的设计直接影响系统的延迟和成本。

最简单的路由策略是基于规则。如果问题中包含因果词（"为什么""影响""导致""结果"），走多步。如果包含并列词（"对比""区别""和""与"），走并行（Query Planning）。其他情况走单步。这种规则路由能覆盖 70-80% 的情况，而且零延迟（不需要模型调用）。

更高级的路由策略是用轻量级模型做分类。输入用户问题，输出"单步/并行/多步"三分类。这种模型可以很小（比如一个微调过的 BERT），延迟只有 10-20ms。但它的准确率比规则高——能处理规则覆盖不了的边界情况。

在实践中，我建议"规则优先 + 模型兆底"。先用规则判断，规则能判断的（70-80%）直接走对应路径。规则不能判断的（20-30%）再用模型分类。这样既保证了低延迟（大部分请求不需要模型调用），又保证了覆盖率（边界情况有模型兆底）。

还有一个重要的路由决策："多步的初始问题是什么"。不是所有问题都适合用用户的原始问题作为第一步。比如用户问"为什么我的高级报表不能用了"，第一步不应该是"为什么高级报表不能用"（太宽泛），而应该是"该用户当前的套餐等级"（具体的探索性查询）。这个"从用户问题到初始查询"的转换，可以用规则（"为什么 X 不能用"→"查用户当前状态"），也可以用模型。

## 生产环境注意事项

在生产环境中运行多步检索时，有几个额外的工程问题需要处理。

首先是超时控制。每一步应该有独立的超时（比如 2 秒），同时所有步骤共享一个总超时（比如 10 秒）。独立超时防止"某一步卡住导致整个流程阻塞"。总超时防止"虽然每步都没超时，但步数太多导致总时间过长"。两个超时缺一不可——只有独立超时，五步各 2 秒就是 10 秒；只有总超时，某一步可能卡 9 秒，留给后续步骤的时间不够。

在实践中，我建议把超时做成可配置的，并且区分"检索超时"和"模型调用超时"。检索超时通常短一些（1-2 秒），因为向量数据库的查询应该很快。模型调用超时可以长一些（3-5 秒），因为模型生成需要时间。如果模型调用经常超时，可能是 prompt 太长了（包含太多证据摘要），需要压缩输入。

其次是 Evidence Store 的全局去重。不同步骤可能从不同数据源检索到相同的文档片段。Evidence Store 应该按 evidence_id（或内容 hash）全局去重——同一条证据不管被几步检索到，只保存一份。这不仅节省存储，也避免"同一条证据被引用两次"导致的答案冗余。

第三是依赖图的记录。每一步的 `depends_on` 字段形成了一个 DAG（有向无环图）。这个 DAG 对于调试和可解释性极有价值。当答案出错时，你可以沿着 DAG 回溯："这个结论来自第 3 步的证据，第 3 步依赖第 1 步的证据，第 1 步的查询是..."。没有 DAG，你只能看到一堆证据，不知道它们之间的因果关系。

第四是并行优化。虽然多步检索整体是串行的，但"无数据依赖的步骤"可以并行。比如第二步"查采购新政策"和第三步"查审批新政策"都只依赖第一步的结果，互不依赖——可以并行执行。这种"层内并行、层间串行"的策略能显著降低总延迟。在实践中，你可以用 DAG 的拓扑排序来确定哪些步骤可以并行。

第五是用户取消的处理。如果用户在多步检索进行中取消了请求，系统应该立即停止未开始的步骤，不要继续浪费资源。已执行的步骤的结果可以缓存（下次相同问题可以复用），但未开始的步骤不应该执行。

在实践中，用户取消的处理比想象中复杂。因为多步检索可能正在并行执行多个步骤（比如第二步和第三步并行），取消时需要同时取消所有正在进行的步骤。如果你用的是 asyncio，可以用 `task.cancel()` 取消所有子任务。如果你用的是线程池，需要用 `Future.cancel()` 或者设置一个全局的 `cancelled` 标志。不管用哪种方式，关键是"取消要快"——不要等当前步骤完成再取消，而是立即中断。

第六是每一步的 Planner 调用都要记录完整的输入和输出。这样当 Bad Case 发生时，你可以"回放"每一步的决策过程：模型看到了什么证据、被要求解决什么问题、生成了什么查询。这种可回放性是多步检索调试的基础——没有它，你只能看到最终结果，无法判断"是哪一步的决策出了问题"。

第七是饱和检测阈值的可配置化。"连续几轮无新信息算饱和"这个阈值不应该是硬编码的——它应该可以通过配置文件调整。对于小数据源（文档少），一轮饱和就够了；对于大数据源（文档多），可能需要两到三轮。把阈值做成配置项，让你可以在不改代码的情况下根据实际效果调优。

第八是多步检索的"降级策略"。如果多步检索的第一步就失败了（比如数据源不可用），系统不应该直接报错——它应该降级为"用原始问题做单步检索"，至少给用户一个"可能不完整但有参考价值"的答案。降级比报错好——用户宁愿看到一个不完整的答案，也不愿意看到一个错误页面。

### 多步检索与多轮对话的结合

在实际的客服场景中，多步检索往往不是孤立发生的——它发生在多轮对话的上下文中。用户可能先问了一个问题，得到了部分答案，然后追问"那审批流程呢？"。这个追问不应该触发一个全新的多步检索——它应该复用上一轮已经收集的证据，只补充缺失的部分。

比如，第一轮用户问"新政策对 Atlas 项目有什么影响"，系统执行了三步检索，收集了采购流程和审批流程的新政策。第二轮用户追问"那合规审查流程呢？"——这时系统已经有了"Atlas 使用采购、审批和合规审查流程"的证据，不需要重新执行第一步，只需要针对"合规审查流程的新政策"做一次补充检索。

这种"增量多步"比"全量多步"更高效——它复用了已有证据，只补充缺失的部分。实现方式是在状态中保存"上一轮的 evidence"，新一轮的 unresolved 只包含"上一轮没解决的 + 用户新追问的"。这样每一步都有"上下文"，而不是从零开始。

但增量多步也有风险：如果上一轮的证据已经过时（比如两轮对话之间政策变了），复用旧证据就会给出错误答案。在实践中，可以给证据加一个 TTL（生存时间）——超过 TTL 的证据不复用，重新检索。对于变化快的数据源（比如工单状态），TTL 可以很短（几分钟）；对于变化慢的数据源（比如政策文档），TTL 可以很长（几小时）。

### 性能与成本优化

多步检索的成本主要来自两个方面：模型调用（每一步都需要模型规划下一步）和向量检索（每一步都需要执行检索）。优化也应该从这两个方面入手。

模型调用优化：第一步的"探索性查询"可以用规则生成，不需要模型。比如"新政策对 X 的影响"的第一步永远是"X 使用哪些流程/组件/模块"——这是一个固定模式，可以用模板生成，不需要模型调用。只有后续步骤（需要根据证据决定查什么）才需要模型。这样可以把模型调用从 3 次减少到 2 次。

检索优化：如果多个步骤查询同一个数据源，可以合并为一次检索（用 OR 条件）。比如"采购流程新政策"和"审批流程新政策"都查同一个文档库，可以合并为"采购流程 OR 审批流程 新政策"一次检索。但这会降低精确度（OR 查询的结果可能不如单独查询精准），所以只在延迟预算紧张时才这么做。

缓存优化：如果同一个问题被多个用户问过，多步检索的结果可以缓存。下次相同问题来时，直接返回缓存结果，不需要重新执行。但缓存的失效策略很重要——如果数据源更新了，缓存的结果可能就过时了。在实践中，可以用"数据源版本号"来控制缓存失效——数据源更新时版本号加 1，缓存的版本号不匹配就失效。

## 如何观测和评测

多步检索的评测比单步检索更复杂——因为你不仅要评测"最终答案对不对"，还要评测"每一步的决策对不对"。这意味着你需要"过程指标"而不只是"结果指标"。结果指标告诉你"答案对不对"，过程指标告诉你"为什么对/为什么错"。

核心指标包括：平均检索步数（每个任务平均几步完成，健康值 2-3 步）、每步新增 evidence 数（每步带来多少新信息，健康值 > 1 条）、重复 fingerprint 拦截数（去重生效的次数，越低越好）、evidence 饱和停止率（因饱和而停止的比例，健康值 < 20%）、多步 vs 单步 Recall 提升（多步带来的召回率提升，健康值 > 20%）。

如果"平均检索步数"经常达到预算上限（比如 4 步），说明要么预算太低，要么 Planner 的查询质量不够好（每步找到的信息太少，需要更多步）。如果"每步新增 evidence 数"经常为 0，说明去重或饱和检测应该更早触发。如果"多步 vs 单步 Recall 提升"不明显（< 10%），说明你的问题大多不需要多步——应该优化路由，让更多问题走单步。

这些指标之间有关联性。比如，如果"平均检索步数"高且"每步新增 evidence 数"低，说明 Planner 在"绕圈子"——每步都在搜，但每步都找不到新东西。这通常意味着 Planner 的查询太宽泛（比如只搜"新政策"而不是"采购流程新政策条款"），或者数据源中确实没有相关内容。区分这两种情况的方法是：检查每步的检索结果是否相关——如果结果相关但重复，是 Planner 的问题；如果结果不相关，是数据源的问题。

Bad Case Debugging 时，应该按照"逐步回放"的方式排查。先看第一步的查询是否正确（是否问对了问题），再看第一步的证据是否充分（是否找到了关键信息），然后看第二步的决策是否合理（是否基于第一步的证据做了正确的推断），依此类推。很多时候，问题出在第一步——如果第一步就查错了方向，后续步骤做得再好也没用。

在实际操作中，我建议你建立一个"多步检索回放工具"：输入一个 task_id，展示每一步的查询、证据、决策理由和状态变化。这种工具让 Bad Case 调试从"猜测"变成"回放"——你不需要猜测"系统为什么这样做"，你可以直接看到"系统当时看到了什么、决定了什么"。

另外，我建议你定期做"多步 vs 单步 A/B 测试"。随机把一部分请求路由到多步检索，另一部分走单步检索（Query Planning），然后比较两组的答案质量和用户满意度。如果多步检索的质量提升不明显（< 10%），但延迟增加了 2-3 倍，那可能意味着你的问题大多不需要多步——应该优化路由策略，让更多问题走单步。反过来，如果多步检索的质量提升显著（> 30%），那值得进一步优化多步的性能（比如层内并行）。

A/B 测试的设计也值得注意。不要只用"答案质量"作为指标——还要看"用户满意度"（用户是否点赞/点踩）、"追问率"（用户是否需要追问才能得到完整答案）、"会话时长"（用户是否很快结束了对话）。有时候答案质量看起来差不多，但多步检索的"追问率"明显更低——因为答案更完整，用户不需要追问。这种"隐性价值"是单纯看答案质量发现不了的。

最后，不要忽略"步数分布"。如果 90% 的任务都在 2 步内完成，但有 5% 的任务需要 4 步以上，那 5% 可能是"特别复杂的问题"或者"Planner 质量不够好"。抽样检查这些高步数任务，看看是"问题确实复杂"还是"Planner 在绕圈子"。如果是后者，优化 Planner 的 prompt 比增加预算更有效。

## 和 RAG / 后端 / 前端的关系

多步检索不是孤立存在的，它和系统的其他部分有明确的交互边界。理解这些边界能帮你避免"职责混乱"——每个组件只做自己的事，通过明确的接口交互。

RAG 层负责每一步的可靠召回。多步检索的"多步"是编排逻辑，但每一步的实际检索还是由 RAG 层完成的。如果单步检索质量不好（召回率低、结果不相关），多步检索也救不了——垃圾进、垃圾出。所以在优化多步检索之前，先确保单步检索的质量。这是一个重要的优先级判断：先优化"每一步的质量"，再优化"步与步之间的编排"。

后端维护 query/evidence DAG 和预算。多步检索的编排逻辑（循环、状态管理、预算控制）应该在后端实现，而不是在模型中。模型只负责"规划下一步查询"，不负责"决定是否停止""是否超预算"——这些确定性判断必须由后端代码控制。

前端可以展示"正在补充哪类证据"的进度信息。比如"正在查找采购流程相关政策...（第 2/4 步）"。但不要展示模型的内部推理（"我认为 Atlas 可能还使用了..."）——用户不需要看到模型的思考过程，只需要看到进度和结果。

Citation Verification 根据依赖链解释答案来源。比如"这个结论来自第 2 步检索的采购文档（ev-003），第 2 步依赖第 1 步的证据（Atlas 使用采购流程）"。这种"依赖链引用"比简单的"来源：文档 X"更有信息量——它告诉用户"为什么系统会去查这个文档"。

理解这些交互边界的重要性在于：它帮你避免"职责混乱"的问题。多步检索的编排逻辑不应该写在模型里（模型不可信），也不应该写在前端里（前端不应该有业务逻辑）。它应该在后端——一个专门的"编排服务"中。这个服务接收任务目标，管理状态，调用 RAG 层执行检索，调用模型规划下一步，最终返回完整的证据集合和步骤记录。

这种设计还有一个实践好处：它让"渐进式开发"成为可能。你可以先实现一个简单的多步检索（只有串行循环，没有并行优化），先上线验证价值。然后再加层内并行、再加饱和检测、再加冲突处理。每一步都是"在已有接口上加功能"，而不是"推倒重来"。如果你的多步检索和 RAG 层紧耦合，这种渐进式开发就不可能——因为每次改编排逻辑都要同时改检索逻辑。

前端与多步检索的交互也值得多说几句。当多步检索正在进行时，前端不应该只是显示一个"加载中..."的 spinner。更好的做法是显示一个结构化的进度："第 1 步：查找 Atlas 项目流程 ✓""第 2 步：查找采购流程新政策..."。这样用户就知道"系统在做什么、做到哪了"，而不是"系统在忙但不知道在忙什么"。这种透明感能显著提升用户信任——用户更愿意等待一个"知道在做什么"的系统，而不是一个"不知道在做什么"的系统。

## 常见疑问 Q&A

**Q: 多步检索和 Query Planning 可以同时使用吗？**

可以，而且推荐这么做。对于"部分有依赖、部分无依赖"的问题，可以先用 Query Planning 拆出独立的子问题并行执行，然后对"有依赖"的部分用多步检索。比如"对比 A 和 B 的定价，并分析新政策的影响"——"A 的定价"和"B 的定价"可以并行（Query Planning），但"新政策的影响"需要先知道"A 和 B 分别用什么流程"（多步检索）。

**Q: 多步检索的延迟会不会太高？**

确实比单步高。典型单步检索 200ms，多步（3 步）约 600ms-1s。但有两个缓解策略：第一，层内并行——无依赖的步骤并行执行，比如第二步和第三步可以同时跑，总延迟从 3×200ms 降到 2×200ms。第二，流式反馈——在检索进行中就向前端推送进度，用户感知到的等待时间更短。

**Q: 如何判断一个问题需要多步还是单步？**

三个信号：包含因果词（"为什么""影响""导致"）、包含链式结构（"先...然后..."）、需要"先查 A 才能查 B"的逻辑。规则优先：用关键词匹配能覆盖 70% 的情况。规则不能判断的，用轻量级模型做分类。

**Q: 多步检索的步数应该限制在多少？**

建议最多 4-5 步。超过 5 步通常意味着问题太复杂（应该让用户缩小范围）或者 Planner 质量不够好（每步找到的信息太少）。实践中，大多数有依赖的问题 2-3 步就够了。

**Q: 如果某一步检索失败了怎么办？**

两种策略：重试一次（换一个措辞），或者跳过这一步继续下一步。如果这一步的结果是后续步骤的前提（比如"先查 Atlas 用什么流程"失败了，后续就没法查"对应政策"），那就应该停止并告诉用户"无法获取必要信息"。如果这一步是"补充性的"（不影响后续步骤），可以跳过。

**Q: 多步检索和 Agent Loop 是什么关系？**

多步检索是 Agent Loop 的一个特化应用。Agent Loop 的通用模式是"观察 → 思考 → 行动 → 观察..."，多步检索把这个模式特化为"检索 → 分析证据 → 规划下一步 → 检索..."。区别在于：Agent Loop 的"行动"可以是任何工具调用（搜索、计算、API 调用），多步检索的"行动"限定为"检索"。这种特化让多步检索更简单、更可控。

**Q: 如何处理多步检索中的"死循环"？**

死循环是指模型反复生成相同或相似的查询，每次都被去重拦截，但模型不知道被拦截了，继续生成相同的查询。修复方法是在去重拦截后，把"这个查询已经执行过"的信息反馈给模型，让它换一个方向。如果连续 3 次被去重拦截，强制停止并报告"无法找到新信息"。

**Q: 多步检索的结果如何与 Citation Verification 配合？**

每一步产生的证据都带有 query_id 和 step_number。当最终答案引用某条证据时，Citation Verification 可以沿着依赖链回溯："这条证据来自第 2 步，第 2 步依赖第 1 步的证据"。这种"链式引用"比简单的"来源：文档 X"更有说服力——它展示了"系统是如何一步步找到这个答案的"。

**Q: 多步检索如何处理"第一步就查不到"的情况？**

这是多步检索最脆弱的环节。如果第一步的探索性查询就没有返回有用结果，后续所有步骤都无法进行。处理策略有三种：第一，重试一次（换一个措辞）；第二，降级为单步检索（用原始问题直接搜）；第三，告诉用户"无法获取必要信息"。选择哪种取决于第一步的重要性——如果第一步是后续所有步骤的前提（比如"Atlas 用什么流程"），失败就应该停止；如果第一步只是"补充信息"，可以跳过继续。

## 不同行业场景中的应用

多步检索在不同行业中有不同的典型模式。理解这些模式能帮你判断"我的场景是否需要多步"以及"多步的结构应该是什么样的"。

在金融行业中，典型的多步场景是"合规审查"。比如"这笔交易是否需要反洗钱审查"。第一步：查交易金额和类型（业务 API）。第二步：根据金额和类型查对应的监管规则（文档检索）。第三步：查该客户的历史交易模式（风控系统 API）。每一步都依赖前一步——如果交易金额低于阈值，就不需要查监管规则了。这种"条件分支"结构在金融场景中很常见——不同的第一步结果会导致完全不同的后续路径。

在医疗行业中，典型的多步场景是"诊断辅助"。比如"这个患者的症状可能是什么原因"。第一步：查患者症状对应的可能疾病（医学知识库）。第二步：根据可能疾病查需要的检查项目（临床指南）。第三步：查患者的历史检查结果（电子病历系统）。这种"逐步缩小范围"的模式和医生看诊的思路完全一致——先间诊（收集症状），再检查（缩小范围），最后诊断（确认结果）。

在法律行业中，典型的多步场景是"案例研究"。比如"这个合同纠纷案件应该怎么处理"。第一步：查合同类型和争议焦点（案件材料）。第二步：根据合同类型查对应的法律条文（法规库）。第三步：查类似案例的判决结果（案例库）。每一步的查询方向都取决于前一步的结果——不同类型的合同适用不同的法律条文，不同的法律条文对应不同的案例。

这些行业场景有一个共同特征：问题的答案不是"一步就能找到"的，而是"需要逐步深入"的。如果你的场景也有这个特征，多步检索就是合适的方案。如果你的场景是"一步就能找到"（比如"年假政策是什么"），就不需要多步。

## 本文小结

让我们回顾一下本文的核心内容。多步检索是 Agentic RAG 中处理"有依赖关系的复杂问题"的检索策略。它的核心特征是"后一步的查询内容由前一步的证据决定"——不是盲目猜测，而是基于证据逐步深入。

从工程角度，多步检索的核心设计决策包括：状态驱动（task + evidence + unresolved + budget 四要素）、已确认实体约束（防止模型猜测）、fingerprint 去重（防止同义重复）、饱和检测（防止无效循环）、预算限制（防止无限检索）、冲突处理（按版本/日期判断，无法判断时披露）。

从实践角度，多步检索最适合"链式依赖"和"先探索后深入"的场景。对于子问题互不依赖的场景，应该用 Query Planning 并行检索。在实际系统中，两者通常组合使用——无依赖的部分并行，有依赖的部分串行。

如果只记住三句话：第一，多步检索的价值是"用证据替代猜测"——每一步都基于事实，而不是模型的想象。第二，"先探索后深入"是最常见的多步结构——第一步搞清楚基本情况，后续步骤针对每个方向深入。第三，停止条件和开始条件同样重要——知道"什么时候该停"和知道"什么时候该开始"一样关键。

这三句话分别对应了多步检索的三个核心问题："为什么要做多步""怎么组织多步""怎么知道做完了"。如果你在任何时候对多步检索的设计感到困惑，回到这三个问题，答案就会清晰。

## 局限性与未来方向

多步检索不是万能的，它有明确的局限性。理解这些局限能帮你避免"过度期待"，也能帮你判断"什么时候该用其他方案"。

第一个局限：多步检索的延迟是累加的。每一步都需要模型调用 + 向量检索，三步就是三倍延迟。对于实时性要求极高的场景（比如用户期望 500ms 内得到响应），多步检索可能不可接受。缓解策略是"层内并行"和"流式反馈"，但根本解决需要"更快的模型"或"更快的检索引擎"。

第二个局限：多步检索的质量严重依赖第一步。如果第一步的"探索性查询"就查错了方向（比如问"Atlas 用什么流程"但数据源里没有这个信息），后续所有步骤都会失败。这种"第一步失败导致全链失败"的问题叫做"错误传播"。缓解策略是"第一步失败时降级为单步检索"，而不是继续后续步骤。

第三个局限：多步检索对 Planner 的质量要求很高。Planner 需要"根据已有证据和未解决问题，生成精准的下一步查询"——这比"一次性生成所有查询"更难。如果 Planner 质量不够好（比如生成的查询太宽泛或太狭窄），多步检索的效果可能还不如单步。在实践中，Planner 的 prompt 设计需要反复调优——这是一个持续的工作，不是一次性的。

未来方向上，多步检索正在向"自适应检索"演进。当前的多步检索是"固定预算"（最多 4 步），未来的多步检索可能是"动态预算"——根据问题的复杂度和每步的结果动态调整预算。简单问题 2 步就停，复杂问题可以走到 6 步。这种"自适应"模式更适合不确定性高的场景。

另一个未来方向是"多步检索 + Agent Memory"。如果系统记住了"上次查 Atlas 项目时，它用了采购和审批两个流程"，下次再问 Atlas 相关问题时，就可以跳过第一步探索，直接从第二步开始。这种"记忆加速"能显著降低多步检索的延迟——但前提是记忆是最新的（如果 Atlas 最近加了新流程，过时的记忆反而会误导）。

还有一个值得关注的方向："多步检索的自动化评测"。当前的评测主要依赖人工检查（抽样看每一步的决策是否合理）。未来，可以用另一个模型做"评审"（LLM-as-Judge），自动检查每一步的查询是否合理、证据是否充分、决策是否正确。这种自动化评测能让你在不增加人力的情况下扩大评测覆盖率——从"每周抽 100 个"变成"每个都检查"。

从更宏观的角度看，多步检索是 Agentic RAG 从"固定管道"向"自主决策"演进的关键一步。传统的 RAG 是"查询 → 检索 → 生成"的固定管道，不管问题是什么，都走同样的流程。多步检索打破了这种固定性——它让系统能够"根据中间结果调整策略"。这种"适应性"是 Agent 和 Pipeline 的核心区别。当你掌握了多步检索，你就已经站在了"从 Pipeline 到 Agent"的转折点上。

## 面试怎么讲

> 多步检索要求后续 query 基于前一步已验证 evidence，状态中保存 query_id、depends_on、evidence_ids 和 unresolved questions。我会用规范化 fingerprint 去重，用 evidence 饱和检测停止，并让所有步骤共享总检索预算。

面试时，建议你用一个具体例子来说明。比如："用户问'新政策对 Atlas 项目有什么影响'，我不会一开始就猜测 Atlas 用什么流程然后并行搜索。我会先查'Atlas 使用哪些流程'，得到'采购流程和审批流程'后，再分别查'采购流程的新政策'和'审批流程的新政策'。每一步的查询内容取决于上一步的证据，而不是模型的猜测。"

然后补充工程细节："我会用 fingerprint 去重防止同义查询浪费预算，用饱和检测防止在搜不到新东西时反复尝试，用预算限制（最多 4 次）防止无限循环。所有步骤记录 depends_on 形成 DAG，方便 Bad Case 调试时逐步回放。"

如果面试官追问"和 Query Planning 的区别"，你可以这样回答："Query Planning 是一次性规划——适合子问题互不依赖的场景，比如'对比 A 和 B'。多步检索是渐进式规划——适合子问题有依赖关系的场景，比如'先查 X 是什么，再查 X 的政策'。在实际系统中，两者可以组合使用：无依赖的部分并行（Planning），有依赖的部分串行（多步）。"

如果面试官追问"如何处理证据冲突"，你可以这样回答："我按版本号或生效日期判断新旧，无法判断时披露冲突让用户确认。绝不自动'猜'哪个对——因为相似度不等于正确性。在企业场景中，错误的自动选择可能导致业务事故。"

## 下一步

下一篇 [241 Tool-Augmented RAG](241.tool-augmented-rag-tutorial.md) 会把文档证据与业务系统实时数据组合起来。多步检索解决的是"在文档库中逐步深入搜索"的问题，但有些信息不在文档里——比如"客户当前的套餐等级"在业务数据库中，"最近的工单状态"在工单系统中。Tool-Augmented RAG 让 Agent 不仅能搜文档，还能调用业务 API 获取实时数据。

从多步检索到 Tool-Augmented RAG 的演进是自然的：多步检索的"行动"限定为"检索文档"，Tool-Augmented RAG 把"行动"扩展为"调用任何工具"。这意味着 Agent 可以在多步循环中交替使用"搜文档"和"调 API"——比如第一步搜文档查政策规则，第二步调 API 查客户当前状态，第三步结合两者生成答案。这种"文档 + 实时数据"的组合是企业级 RAG 的标配。
