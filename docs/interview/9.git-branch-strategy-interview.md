### Q1. 什么是 Feature Flag？在 从「直接 push master」到规范的协作开发 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · Feature Flag |

**参考答法（开发向）：**

**Feature Flag**（功能开关）：用配置控制新功能是否对用户可见。

直觉：代码可以先合进 ，但开关没打开时，用户仍然走旧功能。

**工程语境（从「直接 push master」到规范的协作开发）**：
- 解决什么：把「Feature Flag」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- Feature Flag 和容易混淆的替代方案怎么选？
- 如果去掉 Feature Flag 这一层，最先坏掉的是哪一环？

### Q2. 在 从「直接 push master」到规范的协作开发 相关开发中，判断 Git Flow、GitHub Flow、Trunk-Based Development 分别适合什么团队。 2. 写出清晰的分支名、commit message 和 {#q2}

| 维度 | 说明 |
|------|------|
| 类型 | 实现题 |
| 难度 | 中等 |
| 考点 | 工程能力 |

**参考答法（开发向）：**

**考察点**：判断 Git Flow、GitHub Flow、Trunk-Based Development 分别适合什么团队。 2. 写出清晰的分支名、commit message 和 PR 描述。 3. 知道合并冲突、强制推送、分支保护这些高风险操作该怎么安全处理

**建议回答结构**：
1. **接口/数据**：关键入参、出参、状态字段；
2. **流程**：主路径 + 异常路径（超时、空结果、权限拒绝）；
3. **代码层落点**：放在哪一层（API / Service / Worker / SDK）；
4. **验证**：单测 + 集成测 + 一条可观测指标（日志字段或 metric）。

尽量用「我们服务里 X 模块负责 Y」的方式讲，避免空泛形容词。

|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 典型的 CI 流程 |

**参考答法（开发向）：**

**背景要点**：8d3f2a1 (5 分钟前) fix typo (直接在 master 上改的)

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；

### Q7. 从「直接 push master」到规范的协作开发 能力要上生产，你会优先保证哪三件事？ {#q7}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 从「直接 push master」到规范的协作开发 常见风险点：8d3f2a1 (5 分钟前) fix typo (直接在 master 上改的)

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
