### Q1. 什么是 状态？在 从 useState 到 Zustand、Redux 与 Pin 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · 状态 |

**参考答法（开发向）：**

**状态**（state，状态）：界面在某一刻的「数据快照」——显示什么文字、列表有几条、弹窗开没开、用户选中的 tab 等。

直觉：屏幕背后的**记事本**；记事本变了，React/Vue 重新画界面。

**工程语境（从 useState 到 Zustand、Redux 与 Pin）**：
- 解决什么：把「状态」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- 状态 和容易混淆的替代方案怎么选？
- 如果去掉 状态 这一层，最先坏掉的是哪一环？

**参考答法（开发向）：**

直觉：公司用**共享网盘**代替微信传来传去——Zustand、Redux、Pinia 都是不同品牌的网盘客户端。

### Q5. 生产环境 从 useState 到 Zustand、Redux 与 Pin 出现：把 全塞进 Redux，自己写 //——重复造 Query 的轮子。… —— 排查思路是什么？ {#q5}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：把 全塞进 Redux，自己写 //——重复造 Query 的轮子。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q11. 从 useState 到 Zustand、Redux 与 Pin 能力要上生产，你会优先保证哪三件事？ {#q11}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 从 useState 到 Zustand、Redux 与 Pin 常见风险点：典型场景：知识库助手有 **聊天**、**文档列表**、**侧栏用户信息** 三个区域。聊天里 存了 ；文档页又 拉了一遍 ；用户点了「深色模式」，只有设置页记得 ，回到聊天页又变回浅色——**同一份「应在全站生效」的数据，被复制成多份局部 state**，改一处忘另一处，就是前端里最常见的「状态不同步」。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
