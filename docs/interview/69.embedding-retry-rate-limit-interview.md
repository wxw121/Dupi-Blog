### Q1. 什么是 Rate Limit？在 Embedding API 重试与限流 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · Rate Limit |

**参考答法（开发向）：**

**Rate Limit**（速率限制）：API 服务商对单位时间内请求数（RPM，Requests Per Minute）或 token 数（TPM，Tokens Per Minute）设的上限，超出则拒绝服务，常返回 HTTP **429**。

直觉：**收费站每分钟只放行 N 辆车**——你车队开太快，栏杆放下，得排队等。

**工程语境（Embedding API 重试与限流）**：
- 解决什么：把「Rate Limit」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- Rate Limit 和容易混淆的替代方案怎么选？
- 如果去掉 Rate Limit 这一层，最先坏掉的是哪一环？

### Q2. 什么是 Exponential Backoff？在 Embedding API 重试与限流 相关系统里它承担什么职责？ {#q2}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · Exponential Backoff |

**参考答法（开发向）：**

**Exponential Backoff**（指数退避）：重试时等待时间按指数增长（如 1s、2s、4s、8s），并常加 **Jitter**（随机抖动）避免所有客户端同一秒再撞限流。

直觉：**第一次等 1 秒，第二次等 2 秒，别一百辆车同时按喇叭**。

**工程语境（Embedding API 重试与限流）**：
- 解决什么：把「Exponential Backoff」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- Exponential Backoff 和容易混淆的替代方案怎么选？

### Q9. 生产环境 Embedding API 重试与限流 出现：掩盖「根本修不好」的配置错误（401 被误当 503 重试）。… —— 排查思路是什么？ {#q9}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：掩盖「根本修不好」的配置错误（401 被误当 503 重试）。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q10. 做 Embedding API 重试与限流 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q10}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 Embedding API 重试与限流 全链路。

**通常不在同一层硬做的**（示例）：
- ** 自研 API 网关源码、Kubernetes HPA 自动扩缩、完整分布式事务、各云厂商 SLA 合同谈判。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？

### Q14. Embedding API 重试与限流 能力要上生产，你会优先保证哪三件事？ {#q14}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Embedding API 重试与限流 常见风险点：**Rate Limit**（速率限制）：API 服务商对单位时间内请求数（RPM，Requests Per Minute）或 token 数（TPM，Tokens Per Minute）设的上限，超出则拒绝服务，常返回 HTTP **429**。 通俗说：**收费站每分钟只放行 N 辆车**——你车队开太快，栏杆放下，得排队等。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
