| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · Grounding |

**参考答法（开发向）：**

**Grounding**（落地 / 锚定）：约束模型回答必须基于、且不得超出所提供证据范围的技术与产品策略集合。

直觉：答题卡上的每一句「公司规定」，都要能在你发的 **参考资料** 里找到对应句子；找不到就停笔。

- 解决什么：把「Grounding」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- Grounding 和容易混淆的替代方案怎么选？

### Q9. 生产环境 Grounding 与引用归因 出现：1. **以为 RAG 等于不会幻觉**——检索错、截断、模型忽视资料仍会错；见 33 篇。 2. **只在前端展示「来… —— 排查思路是什么？ {#q9}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：1. **以为 RAG 等于不会幻觉**——检索错、截断、模型忽视资料仍会错；见 33 篇。 2. **只在前端展示「来源文档名」**——正文数字错仍无法追责；要句级引用。 3. **多轮对话把旧答案当证据**——每轮重新绑检索 chunk。 4. **矛盾资料强行综合**——应暴露矛盾或走人工。 5. **用 CoT 替代 Grounding**——长推理不能代替 。 6. **拒答率羞耻**——高拒答有时说明边界清晰；关键是引导下一步。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q13. 做 Grounding 与引用归因 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q13}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 Grounding 与引用归因 全链路。

**通常不在同一层硬做的**（示例）：
- ** 完整引用卡片 React 组件、RAGAS Faithfulness 公式与自动化评测流水线（E 轨）、法律免责声明起草、多跳 Agent 工具链、向量检索本身怎么调（见 C/D 轨）。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？

结合 Grounding 与引用归因 常见风险点：客服截图里最常见的一句质问是：「你们机器人说年假 20 天，手册写 10 天——依据呢？」 若你只能回答「模型是这么生成的」，产品就输了。用户要的是 **可核对**：点开引用，看到第几章第几条；若资料里没有，就明确说 **不知道**，而不是用流畅语气把缺口糊上。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
