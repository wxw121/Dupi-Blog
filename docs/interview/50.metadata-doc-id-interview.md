### Q1. 什么是 doc_id？在 doc_id 元数据 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · doc_id |

**参考答法（开发向）：**

**doc_id**（Document Identifier，文档标识符）：在系统内唯一标识 **一份逻辑文档** 的稳定字符串，不随物理路径、显示文件名、单次上传批次变化。

直觉：**身份证号**——改名换地址，号不变。

**工程语境（doc_id 元数据）**：
- 解决什么：把「doc_id」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- doc_id 和容易混淆的替代方案怎么选？
- 如果去掉 doc_id 这一层，最先坏掉的是哪一环？

### Q13. 做 doc_id 元数据 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q13}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 doc_id 元数据 全链路。

**通常不在同一层硬做的**（示例）：
- ** 多租户行级安全、全球分布式 ID（Snowflake）、区块链内容寻址、GraphRAG 实体 ID。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？
