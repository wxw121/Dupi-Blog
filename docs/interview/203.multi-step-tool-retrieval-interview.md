### Q1. 如何设计/实现「为什么需要多步工具检索」？（Multi-step Tool Retrieval 完全指南（了） {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 为什么需要多步工具检索 |

**参考答法（开发向）：**

**背景要点**：普通 RAG 默认只有一个检索动作。用户问问题，系统查知识库，模型回答。这个流程清晰、便宜、稳定，但处理不了所有问题。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

**常见追问：**

- MVP 版本可以砍掉哪些部分？

### Q4. 生产环境 Multi-step Tool Retrieval 完全指南（了 出现：| 停止条件 | 说明 | |----------|------| | | 模型认为证据足够 | | | 达到最大步数 … —— 排查思路是什么？ {#q4}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：| 停止条件 | 说明 | |----------|------| | | 模型认为证据足够 | | | 达到最大步数 | | | 连续两步没有新证据 | | | 工具错误过多 | | | 权限或安全规则拒绝 |

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

### Q10. Multi-step Tool Retrieval 完全指南（了 能力要上生产，你会优先保证哪三件事？ {#q10}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Multi-step Tool Retrieval 完全指南（了 常见风险点：普通 RAG 默认只有一个检索动作。用户问问题，系统查知识库，模型回答。这个流程清晰、便宜、稳定，但处理不了所有问题。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
