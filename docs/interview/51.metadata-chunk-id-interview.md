### Q1. 什么是 chunk_id？在 chunk_id 元数据 相关系统里它承担什么职责？ {#q1}

|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · chunk_id |

**参考答法（开发向）：**

**chunk_id**（Chunk Identifier，块标识符）：在 （及通常 ）语境下，唯一标识一个 **文本块** 的字符串，用于向量库主键、引用、日志与评测对齐。

直觉：**书中某一页的某一段，有独立页签号**。

### Q9. 生产环境 chunk_id 元数据 出现：下面这些错误看起来都很小：少拼一个 version、复用一个序号、把页码当主键。但在真实系统里，它们会让旧文档、新文档和… —— 排查思路是什么？ {#q9}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：下面这些错误看起来都很小：少拼一个 version、复用一个序号、把页码当主键。但在真实系统里，它们会让旧文档、新文档和相邻 chunk 混在一起，最终表现成“引用对不上”或“明明改了制度，答案还是旧的”。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q13. 做 chunk_id 元数据 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q13}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 chunk_id 元数据 全链路。

**通常不在同一层硬做的**（示例）：
- ** 子句级 span 对齐、LayoutLM 字符 offset、多模态图块 ID、GraphRAG 实体节点 ID。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？
