### Q9. 生产环境 Markdown 解析 出现：1. **正则解析 Markdown** —— 代码块里的 ` 进索引会污染检索。 3. **H1 切块过碎** —— … —— 排查思路是什么？ {#q9}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：1. **正则解析 Markdown** —— 代码块里的 ` 进索引会污染检索。 3. **H1 切块过碎** —— 单文件文档常以 **H2** 为界，H1 作全书标题。 4. **代码块当普通文本 embedding** —— 可存，但问答配置类建议加 **关键词或单独索引**。 5. **Wiki 扩展语法当标准 MD** —— 换解析器或预处理宏。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q13. 做 Markdown 解析 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q13}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 Markdown 解析 全链路。

**通常不在同一层硬做的**（示例）：
- ** 完整 CommonMark 规范逐条、自定义渲染主题、MDX/React 组件、Wiki 专有语法全家桶。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？

### Q17. Markdown 解析 能力要上生产，你会优先保证哪三件事？ {#q17}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Markdown 解析 常见风险点：**Markdown**：一种轻量标记语言，用少量符号（、、``` 等）在纯文本里表达 **标题、列表、强调、代码** 等结构。 通俗说：**写字时顺手打标记，渲染后像排版好的网页**。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。
