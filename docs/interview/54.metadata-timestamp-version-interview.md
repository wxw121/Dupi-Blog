### Q1. 什么是 Timestamp metadata？在 Timestamp / Version 时效元数据 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · Timestamp metadata |

**参考答法（开发向）：**

**Timestamp metadata**（时间戳元数据）：描述文档或 chunk 在时间轴上位置的字段，如创建、修改、生效、入库时间。

直觉：给知识贴 **「什么时候还算数」** 的标签。

**工程语境（Timestamp / Version 时效元数据）**：
- 解决什么：把「Timestamp metadata」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- Timestamp metadata 和容易混淆的替代方案怎么选？
- 如果去掉 Timestamp metadata 这一层，最先坏掉的是哪一环？

### Q9. 做 Timestamp / Version 时效元数据 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q9}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 Timestamp / Version 时效元数据 全链路。

**通常不在同一层硬做的**（示例）：
- ** 增量更新流水线代码（路线图 **56** 全文）、事件溯源架构、时区法务认定、实时新闻秒级爬虫。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？

### Q13. Timestamp / Version 时效元数据 能力要上生产，你会优先保证哪三件事？ {#q13}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Timestamp / Version 时效元数据 常见风险点：用户问：「研发加班补贴标准是多少？」检索命中 2021 年旧版制度：**每晚 200 元**；2024 年新规已是 **300 元**。两段文字 **语义相近**，向量分数可能差 0.02——若无 **时间元数据**，系统会把旧规当权威，还配上 **「员工手册 p.8 [1]」** 的完美引用。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
