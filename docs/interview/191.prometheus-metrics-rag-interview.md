### Q1. 如何设计/实现「第一批上线最小集」？（Prometheus 指标） {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 第一批上线最小集 |

**参考答法（开发向）：**

**背景要点**：没有指标的系统只能靠用户投诉和日志排查。RAG 系统尤其容易出现“慢慢变坏”的问题：队列积压越来越多、向量库查询越来越慢、embedding token 成本突然升高、P95 延迟逐步爬升。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

**常见追问：**

- MVP 版本可以砍掉哪些部分？
- 10x 流量时最先改什么？

### Q3. 生产环境 Prometheus 指标 出现：| 现象 | 检查 | |------|------| | target down | 端口、防火墙、服务是否监听 0.… —— 排查思路是什么？ {#q3}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：| 现象 | 检查 | |------|------| | target down | 端口、防火墙、服务是否监听 0.0.0.0 | | 无自定义指标 | 是否 import 了 prometheus_client、是否打到请求路径 | | 数据断层 | Prometheus 自身磁盘、保留时间 |

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q9. Prometheus 指标 能力要上生产，你会优先保证哪三件事？ {#q9}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Prometheus 指标 常见风险点：没有指标的系统只能靠用户投诉和日志排查。RAG 系统尤其容易出现“慢慢变坏”的问题：队列积压越来越多、向量库查询越来越慢、embedding token 成本突然升高、P95 延迟逐步爬升。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
