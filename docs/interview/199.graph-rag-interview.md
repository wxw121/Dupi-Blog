### Q1. 什么是 Graph RAG？在 Graph RAG 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · Graph RAG |

**参考答法（开发向）：**

**Graph RAG**（Graph-based Retrieval-Augmented Generation）：以 **知识图谱式结构**（节点、边、社区）增强检索与上下文组织，使 **全局聚合与关系推理** 有显式载体。通俗说：**先画人物关系网并写「圈子梗概」，再问「整个圈子在讨论什么」**。

**工程语境（Graph RAG）**：
- 解决什么：把「Graph RAG」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- Graph RAG 和容易混淆的替代方案怎么选？
- 如果去掉 Graph RAG 这一层，最先坏掉的是哪一环？

### Q9. 生产环境 Graph RAG 出现：翻车多源于把 GraphRAG 当万能开关：全库替代向量、小语料期望奇迹、抽图用小模型不评测、社区摘要不随文档更新、忽视… —— 排查思路是什么？ {#q9}

|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：翻车多源于把 GraphRAG 当万能开关：全库替代向量、小语料期望奇迹、抽图用小模型不评测、社区摘要不随文档更新、忽视 index 阶段 LLM 费用。每条都应在 PoC 检查清单里勾选，再决定是否扩大语料。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

### Q13. 做 Graph RAG 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q13}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 Graph RAG 全链路。

**通常不在同一层硬做的**（示例）：
- ** Neo4j 全栈运维、自研图神经网络、每版 GraphRAG YAML 全参数。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？
