### Q1. 什么是 BM25？在 BM25 稀疏检索原理 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · BM25 |

**参考答法（开发向）：**

**BM25**（Okapi BM25）：基于 **概率相关度模型**（Probabilistic IR）的排序函数，对查询 term 与文档的相关性打分；Elasticsearch 7.x 起默认取代纯 TF-IDF 作为文本相似度。

直觉：**仍看关键词命中**，但「同一词多出现几次」收益递减，「文档特别长」不能自动赢。

**工程语境（BM25 稀疏检索原理）**：
- 解决什么：把「BM25」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- BM25 和容易混淆的替代方案怎么选？
- 如果去掉 BM25 这一层，最先坏掉的是哪一环？

### Q9. 生产环境 BM25 稀疏检索原理 出现：**陷阱 1**：把 ES 的 当 0～1 概率。 **陷阱 2**：查询未分词与索引不一致。 **陷阱 3**：极小语… —— 排查思路是什么？ {#q9}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：**陷阱 1**：把 ES 的 当 0～1 概率。 **陷阱 2**：查询未分词与索引不一致。 **陷阱 3**：极小语料（几十 chunk）上 idf 极端，BM25 波动大——需更多数据或平滑。 **陷阱 4**：只调 k1、b 不修 **chunk 边界** 切断关键词。 **陷阱 5**：以为 BM25 能匹配「汽车↔轿车」——需向量或同义词表。 **陷阱 6**：全库重建后未 **refresh** 索引统计，avgdl、df 陈旧（ES 最终一致）。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q16. BM25 稀疏检索原理 能力要上生产，你会优先保证哪三件事？ {#q16}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 BM25 稀疏检索原理 常见风险点：典型场景：制度库 2 万个 chunk，用户问「年假报销流程」。TF-IDF 余弦能排出前几名，但你发现：**一篇 2000 字的《员工手册》总则** 因词多、命中多，总压在 **300 字的《年假管理办法》** 上；还有篇 FAQ 里「报销」一词出现二十次，分数爆炸。Elasticsearch 开箱的 **similarity: BM25** 正是为缓解这类现象设计的。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

- 如何做成本归因到租户/业务线？
