### Q1. 如何设计/实现「为什么检索结果会重复」？（检索结果去重） {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 为什么检索结果会重复 |

**参考答法（开发向）：**

**背景要点**：重复不一定是完全相同的字符串。它可能是同一个 ，也可能是同一页的相邻 chunk，甚至是两个版本里几乎相同的段落。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

**常见追问：**

- MVP 版本可以砍掉哪些部分？
- 10x 流量时最先改什么？

### Q2. 如何设计/实现「最小 Python 实现」？（检索结果去重） {#q2}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 最小 Python 实现 |

**参考答法（开发向）：**

**背景要点**：在企业知识库里，重复往往来自 **多路召回叠加**：向量检索按语义相似度排序，BM25 按关键词命中，多查询改写又会从不同角度再搜一遍。三路结果合并后，同一段制度条文出现三次并不罕见。如果不去重，精排模型和 MMR 都要对重复 chunk 重复打分，浪费算力；更糟的是，最终上下文里前五条可能都在讲同一件事，用户问的是“住宿上限 **和** 审批流程”，模型却只看到上限。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

**常见追问：**

- MVP 版本可以砍掉哪些部分？
- 10x 流量时最先改什么？

### Q9. 检索结果去重 能力要上生产，你会优先保证哪三件事？ {#q9}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 检索结果去重 常见风险点：重复不一定是完全相同的字符串。它可能是同一个 ，也可能是同一页的相邻 chunk，甚至是两个版本里几乎相同的段落。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？

### Q10. 用 2 分钟讲清楚 检索结果去重 的技术方案（面向面试官）。 {#q10}

|------|------|
| 类型 | 综合题 |
| 难度 | 高频 |
| 考点 | 技术表述 |

**参考答法（开发向）：**

**30 秒版**：问题背景 → 核心组件 → 一条量化结果。

**2 分钟版**（可按链路讲）：为什么检索结果会重复 → 去重要解决什么问题 → 三层去重：id、文档、语义 → 在 RAG 链路中的位置

每层补一句：**输入输出 + 失败怎么办**。
避免背章节标题；用「请求进来以后……」的叙事更自然。

**常见追问：**

- 如果面试官只给白板，你会先画哪张图？
