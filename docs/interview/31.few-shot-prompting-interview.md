### Q1. 什么是 Few-shot Prompting？在 Few-shot Prompting（少样本提示） 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · Few-shot Prompting |

**参考答法（开发向）：**

**Few-shot Prompting**（少样本提示）：在提示中提供 **少量输入–输出示例**，引导模型对 **新输入** 产生同类输出的技术。

直觉：先做两道例题再考试，而不是只发一张空白答题卡。

**工程语境（Few-shot Prompting（少样本提示））**：
- 解决什么：把「Few-shot Prompting」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- Few-shot Prompting 和容易混淆的替代方案怎么选？
- 如果去掉 Few-shot Prompting 这一层，最先坏掉的是哪一环？

### Q5. 如何设计/实现「最小实战：用 2 个例子锁定 JSON 字段」？（Few-shot Prompting（少样本提示）） {#q5}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 最小实战：用 2 个例子锁定 JSON  |

**参考答法（开发向）：**

**背景要点**：你对模型说：「把工单分成三类：报销 / 请假 / 其他，输出 JSON。」 有时它输出 Markdown 表格；有时字段名写成 有时写成 ；有时还顺便写一段安慰人的话。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

**常见追问：**

- MVP 版本可以砍掉哪些部分？
- 10x 流量时最先改什么？

### Q6. 生产环境 Few-shot Prompting（少样本提示） 出现：**误用 1：** 把制度全文拆成「假 few-shot 问答」塞进提示，却不做检索。 → 窗口立刻爆；也难更新。该走 … —— 排查思路是什么？ {#q6}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：**误用 1：** 把制度全文拆成「假 few-shot 问答」塞进提示，却不做检索。 → 窗口立刻爆；也难更新。该走 RAG。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q10. 做 Few-shot Prompting（少样本提示） 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q10}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 Few-shot Prompting（少样本提示） 全链路。

**通常不在同一层硬做的**（示例）：
- ** 自动选例子的检索式 ICL、提示词优化算法、完整微调数据集构建、Agent 工具选择的 few-shot。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？

| 维度 | 说明 |
|------|------|
| 类型 | 对比题 |
| 难度 | 中等 |
| 考点 | 对比 · Few-shot Prompting vs In-context learning |

**参考答法（开发向）：**

| 维度 | Few-shot Prompting | In-context learning |
|------|----------|----------|
| 定义 | 在提示中提供 **少量输入–输出示例**，引导模型对 **新输入** 产生同类输出的技术。 | 不更新模型参数，仅靠当前提示里的说明与例子改变行为的现象。 |

- 给出「默认选谁 + 何时叠加谁」，必要时 Hybrid；

### Q14. Few-shot Prompting（少样本提示） 能力要上生产，你会优先保证哪三件事？ {#q14}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Few-shot Prompting（少样本提示） 常见风险点：你对模型说：「把工单分成三类：报销 / 请假 / 其他，输出 JSON。」 有时它输出 Markdown 表格；有时字段名写成 有时写成 ；有时还顺便写一段安慰人的话。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？

### Q15. 用 2 分钟讲清楚 Few-shot Prompting（少样本提示） 的技术方案（面向面试官）。 {#q15}

| 维度 | 说明 |
|------|------|
| 类型 | 综合题 |
| 难度 | 高频 |
| 考点 | 技术表述 |

**参考答法（开发向）：**

**30 秒版**：问题背景 → 核心组件 → 一条量化结果。

**2 分钟版**（可按链路讲）：本文边界 → 零样本、单样本、少样本 → Zero-shot（零样本） → One-shot（单样本）

每层补一句：**输入输出 + 失败怎么办**。
避免背章节标题；用「请求进来以后……」的叙事更自然。

**常见追问：**

- 如果面试官只给白板，你会先画哪张图？
- 你最自豪的一次优化是什么？
