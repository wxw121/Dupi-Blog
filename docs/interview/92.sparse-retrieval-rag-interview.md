### Q1. 什么是 倒排索引？在 Sparse Retrieval 稀疏检索 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · 倒排索引 |

**参考答法（开发向）：**

**倒排索引**（Inverted Index）：从“词”指向“包含该词的文档列表”的索引结构。

直觉：字典的反向查法——不是从文档找词，而是从词找文档。

**工程语境（Sparse Retrieval 稀疏检索）**：
- 解决什么：把「倒排索引」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- 倒排索引 和容易混淆的替代方案怎么选？
- 如果去掉 倒排索引 这一层，最先坏掉的是哪一环？

### Q8. Sparse Retrieval 稀疏检索 能力要上生产，你会优先保证哪三件事？ {#q8}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Sparse Retrieval 稀疏检索 常见风险点：很多初学者一学 RAG 就想全靠 embedding。问题是：企业文档里有大量编号、产品名、错误码、制度条款、API 名称。比如用户搜 、、，这些并不一定靠语义向量稳定命中。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
