### Q1. 如何设计/实现「分检索器设阈值」？（Score Threshold 分数阈值检索指南） {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 分检索器设阈值 |

**参考答法（开发向）：**

**背景要点**：用户可能问知识库没有覆盖的问题。如果系统无论如何都取 top-5 给模型，模型就可能基于弱相关 chunk 硬编答案。分数阈值的作用是给检索结果设置最低相关性要求。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

**常见追问：**

- MVP 版本可以砍掉哪些部分？
- 10x 流量时最先改什么？

### Q5. 生产环境 Score Threshold 分数阈值检索指南 出现：发版最常见翻车是“升级 embedding 未重标 τ”：有答案集最高分从 0.85 降到 0.62，旧 τ=0.72 … —— 排查思路是什么？ {#q5}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：发版最常见翻车是“升级 embedding 未重标 τ”：有答案集最高分从 0.85 降到 0.62，旧 τ=0.72 导致大面积误拒。应在配置中心把 与 绑成一条记录，CI 检测到模型变更时阻断部署，直到评测集重跑通过。灰度期可用 shadow 模式对比新旧 τ 的拒答差异，再全量切换。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q10. Score Threshold 分数阈值检索指南 能力要上生产，你会优先保证哪三件事？ {#q10}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Score Threshold 分数阈值检索指南 常见风险点：用户可能问知识库没有覆盖的问题。如果系统无论如何都取 top-5 给模型，模型就可能基于弱相关 chunk 硬编答案。分数阈值的作用是给检索结果设置最低相关性要求。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
