### Q1. 什么是 Hybrid Search？在 Hybrid Search 混合检索 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · Hybrid Search |

**参考答法（开发向）：**

**Hybrid Search**（混合检索）：把 Dense Retrieval 和 Sparse Retrieval 结合起来，同时利用语义相似和关键词命中。

直觉：既让系统听懂“意思”，也让它认得“原词、编号、错误码”。

**工程语境（Hybrid Search 混合检索）**：
- 解决什么：把「Hybrid Search」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- Hybrid Search 和容易混淆的替代方案怎么选？
- 如果去掉 Hybrid Search 这一层，最先坏掉的是哪一环？

### Q6. 生产环境 Hybrid Search 混合检索 出现：若 Sparse 路超时，可仅用 Dense + 告警，而非整链失败；反之亦然。Hybrid 的优势是 **单路容错**… —— 排查思路是什么？ {#q6}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：若 Sparse 路超时，可仅用 Dense + 告警，而非整链失败；反之亦然。Hybrid 的优势是 **单路容错**，但要在监控里看见降级率，防止 Sparse 路长期挂掉却无人知。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q12. Hybrid Search 混合检索 能力要上生产，你会优先保证哪三件事？ {#q12}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Hybrid Search 混合检索 常见风险点：只用 Dense，可能漏掉标准号、错误码、API 名称；只用 Sparse，可能漏掉同义表达和自然语言改写。企业 RAG 用户既会问“报销住宿上限”，也会搜“GB/T 12345”。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
