### Q1. 如何设计/实现「三层闸门：检索、评分、生成」？（RAG 拒答策略） {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 三层闸门：检索、评分、生成 |

**参考答法（开发向）：**

**背景要点**：RAG 的答案应该来自检索到的资料。如果没有资料、资料不相关，或者用户无权查看资料，模型继续回答就会变成猜测。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

**常见追问：**

- MVP 版本可以砍掉哪些部分？
- 10x 流量时最先改什么？

### Q2. 如何设计/实现「最小 Python 判定器」？（RAG 拒答策略） {#q2}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 最小 Python 判定器 |

**参考答法（开发向）：**

**背景要点**：拒答不是产品失败，而是可靠性的一部分。尤其在企业知识库、法务、医疗、财务、合规场景中，错误回答比“不确定”更危险。产品侧应把拒答设计成**可预期的边界行为**：用户知道系统何时不能答、下一步该补充什么资料，而不是在流畅段落里混入未经证实的推断。

### Q11. RAG 拒答策略 能力要上生产，你会优先保证哪三件事？ {#q11}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 RAG 拒答策略 常见风险点：RAG 的答案应该来自检索到的资料。如果没有资料、资料不相关，或者用户无权查看资料，模型继续回答就会变成猜测。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？

### Q12. 用 2 分钟讲清楚 RAG 拒答策略 的技术方案（面向面试官）。 {#q12}

| 维度 | 说明 |
|------|------|
| 类型 | 综合题 |
| 难度 | 高频 |
| 考点 | 技术表述 |

**参考答法（开发向）：**

**30 秒版**：问题背景 → 核心组件 → 一条量化结果。

**2 分钟版**（可按链路讲）：为什么 RAG 需要拒答 → 拒答和澄清的区别 → 三层闸门：检索、评分、生成 → 拒答话术模板

每层补一句：**输入输出 + 失败怎么办**。
避免背章节标题；用「请求进来以后……」的叙事更自然。

**常见追问：**

- 如果面试官只给白板，你会先画哪张图？
- 你最自豪的一次优化是什么？
