### Q1. 什么是 ACL？在 ACL 访问控制元数据 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · ACL |

**参考答法（开发向）：**

**ACL**（Access Control List，访问控制列表）：描述主体（用户/角色/租户）对客体（文档/chunk）是否有权访问的规则集合；在 RAG 中常落为 **chunk 元数据 + 检索过滤**。

直觉：每个 chunk 贴一张 **「给谁看」** 的标签；问问题时 **只许带用户有权看的标签** 进候选。

**工程语境（ACL 访问控制元数据）**：
- 解决什么：把「ACL」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- ACL 和容易混淆的替代方案怎么选？
- 如果去掉 ACL 这一层，最先坏掉的是哪一环？

| 难度 | 中等 |
| 考点 | 工程设计 · 前言：RAG 的泄密面在检索，不在「模型 |

**参考答法（开发向）：**

**背景要点**：企业知识库几乎都不是「全员一份只读 Wiki」。财务制度、并购纪要、个人薪资说明、客户合同——**可见范围不同**。传统搜索靠登录态 + 文档库权限；RAG 若把 **所有 chunk 嵌入同一向量空间**，却在查询时不带 **身份与角色**，就等于 **把保密柜钥匙插在门锁上**。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；

4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

### Q13. 做 ACL 访问控制元数据 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q13}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 ACL 访问控制元数据 全链路。

**通常不在同一层硬做的**（示例）：
- ** OAuth2/OIDC 完整实现、LDAP 同步、行级数据库安全、密级定标合规流程、Kubernetes NetworkPolicy。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？

### Q14. ACL 和 Multi-tenancy 有什么区别？在 ACL 访问控制元数据 里如何选型？ {#q14}

| 维度 | 说明 |
|------|------|
| 类型 | 对比题 |
| 难度 | 中等 |
| 考点 | 对比 · ACL vs Multi-tenancy |

**参考答法（开发向）：**

| 维度 | ACL | Multi-tenancy |
|------|----------|----------|
| 定义 | 描述主体（用户/角色/租户）对客体（文档/chunk）是否有权访问的规则集合；在 RAG 中常落为 **chunk 元数据 + 检索过滤**。 | 同一套 RAG 服务承载多个客户或事业部，数据与权限 **硬隔离**。 |
| 适用 | 见具体场景约束 | 见具体场景约束 |

**选型建议**：
- 用 **输入形态**（精确词 vs 语义改写）、**延迟预算**、**运维成本** 三张表说话；
- 给出「默认选谁 + 何时叠加谁」，必要时 Hybrid；
- 用评测集证明，而不是团队偏好。

### Q17. ACL 访问控制元数据 能力要上生产，你会优先保证哪三件事？ {#q17}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 ACL 访问控制元数据 常见风险点：企业知识库几乎都不是「全员一份只读 Wiki」。财务制度、并购纪要、个人薪资说明、客户合同——**可见范围不同**。传统搜索靠登录态 + 文档库权限；RAG 若把 **所有 chunk 嵌入同一向量空间**，却在查询时不带 **身份与角色**，就等于 **把保密柜钥匙插在门锁上**。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

- 如何做成本归因到租户/业务线？
