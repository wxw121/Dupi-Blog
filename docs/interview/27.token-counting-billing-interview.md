### Q1. 什么是 Token？在 Token 计数与计费 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · Token |

**参考答法（开发向）：**

**Token**（词元 / 子词单元）：语言模型在内部使用的 **文本切分单位**。训练与推理时，字符串先被 tokenizer 切成 token 序列，再映射成整数 ID 送进模型。

直觉：模型不直接「看汉字或英文单词」，而看一串它自己的「积木块」；计费和长度限制，多半按积木块个数算。

**工程语境（Token 计数与计费）**：
- 解决什么：把「Token」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- Token 和容易混淆的替代方案怎么选？
- 如果去掉 Token 这一层，最先坏掉的是哪一环？

### Q5. 如何设计/实现「上线前的最小验收清单」？（Token 计数与计费） {#q5}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 上线前的最小验收清单 |

**参考答法（开发向）：**

**背景要点**：1. **报错**： / 「超过最大上下文」——明明「字数看起来还行」。 2. **账单**：同样「聊了几句」，费用比预期高一个数量级——因为每次请求都带了长系统提示 + 多段检索资料 + 历史轮次。 3. **误解**：运营按「汉字个数 × 单价」估算成本，和财务对不上。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

**常见追问：**

- MVP 版本可以砍掉哪些部分？
- 10x 流量时最先改什么？

### Q13. Token 计数与计费 能力要上生产，你会优先保证哪三件事？ {#q13}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Token 计数与计费 常见风险点：1. **报错**： / 「超过最大上下文」——明明「字数看起来还行」。 2. **账单**：同样「聊了几句」，费用比预期高一个数量级——因为每次请求都带了长系统提示 + 多段检索资料 + 历史轮次。 3. **误解**：运营按「汉字个数 × 单价」估算成本，和财务对不上。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
