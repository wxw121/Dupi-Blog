### Q1. 什么是 RAG？在 FastAPI RAG 项目结构 相关系统里它承担什么职责？ {#q1}

| 维度 | 说明 |
|------|------|
| 类型 | 概念题 |
| 难度 | 基础 |
| 考点 | 核心概念 · RAG |

**参考答法（开发向）：**

**RAG**（Retrieval-Augmented Generation，检索增强生成）：先从知识库找资料，再让大模型基于资料回答。

直觉：它不是让模型凭记忆答题，而是先翻资料再开口。

**工程语境（FastAPI RAG 项目结构）**：
- 解决什么：把「RAG」讲清楚时，要落到 **输入/输出、放在链路哪一层、失败时怎么办**；
- 常见误用：只会背定义，说不出和相邻组件的分工；
- 加分项：举一个线上或 demo 中的真实调用点（接口、配置项、监控指标）。

**常见追问：**

- RAG 和容易混淆的替代方案怎么选？
- 如果去掉 RAG 这一层，最先坏掉的是哪一环？

### Q3. 如何设计/实现「与索引和评测模块如何连接」？（FastAPI RAG 项目结构） {#q3}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 与索引和评测模块如何连接 |

**参考答法（开发向）：**

**背景要点**：RAG 项目的后端通常会同时处理四类事情：对外提供 API、接收上传文件、触发后台索引任务、调用检索与生成服务。把它们写进一个文件，会让每次修改都很危险，因为你无法判断改一个接口会不会影响另一个接口。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

**常见追问：**

- MVP 版本可以砍掉哪些部分？
- 10x 流量时最先改什么？

### Q5. 生产环境 FastAPI RAG 项目结构 出现：写你的业务规则； 负责调用外部系统，例如模型 API、向量数据库、对象存储。… —— 排查思路是什么？ {#q5}

| 维度 | 说明 |
|------|------|
| 类型 | 排障题 |
| 难度 | 中等 |
| 考点 | 线上排障 |

**参考答法（开发向）：**

**现象摘要**：写你的业务规则； 负责调用外部系统，例如模型 API、向量数据库、对象存储。

**排查顺序**：
1. **范围**：影响面、开始时间、是否可回滚；
2. **证据链**：请求 ID → 各 hop 日志（网关 / 应用 / 向量库 / 模型 / 工具）；
3. **分层假设**：数据污染、配置变更、依赖超时、逻辑 bug——每次只验证一个；
4. **止血**：降级（缓存答案、缩小 top_k、关闭非关键工具）、限流；
5. **根因与回归**：补集成测试 + 告警阈值。

**常见追问：**

- 如何写一份给 on-call 的 runbook？
- 哪些信息必须打进结构化日志？

### Q11. FastAPI RAG 项目结构 能力要上生产，你会优先保证哪三件事？ {#q11}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 FastAPI RAG 项目结构 常见风险点：RAG 项目的后端通常会同时处理四类事情：对外提供 API、接收上传文件、触发后台索引任务、调用检索与生成服务。把它们写进一个文件，会让每次修改都很危险，因为你无法判断改一个接口会不会影响另一个接口。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
