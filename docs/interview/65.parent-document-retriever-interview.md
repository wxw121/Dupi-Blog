### Q5. 如何设计/实现「读完本篇的最小交付物」？（Parent-Document Retriever） {#q5}

| 维度 | 说明 |
|------|------|
| 类型 | 设计题 |
| 难度 | 中等 |
| 考点 | 工程设计 · 读完本篇的最小交付物 |

**参考答法（开发向）：**

**背景要点**：**Parent-Document Retriever**（父文档检索器）：一种 RAG 索引策略——将文档先切成较大的 **父块**（Parent Chunk，通常对应章节），再在每个父块内切成较小的 **子块**（Child Chunk）仅用于 **向量检索**；检索命中子块后，取出关联 **父块全文**（或更大上下文）交给 LLM 生成答案。 通俗说：**用「小纸条」找位置，用「整页纸」给模型读**——检索找得准，生成读得全。

**设计回答框架**：
1. **目标与约束**：延迟、准确率、成本、团队规模；
2. **组件图**：列出 3～5 个模块及数据流（可手绘）；
3. **关键接口**：同步 API / 消息 / 批处理任务各负责什么；
4. **失败与降级**：超时、空检索、工具失败时的默认策略；
5. **评测**：离线指标 + 线上 shadow / 金丝雀。

### Q13. 做 Parent-Document Retriever 时，哪些能力应在当前服务内实现，哪些应下沉到专用组件或另开服务？ {#q13}

| 维度 | 说明 |
|------|------|
| 类型 | 架构边界 |
| 难度 | 中等 |
| 考点 | 架构分层 |

**参考答法（开发向）：**

考察 **分层与职责单一**，避免一个服务包揽 Parent-Document Retriever 全链路。

**通常不在同一层硬做的**（示例）：
- ** LangChain 全家桶 API 逐参数、多向量库厂商语法、GraphRAG 实体索引、ColBERT late interaction。

**答题要点**：
- 当前层只保留 **决策 + 编排 + 领域状态**；
- IO 密集（向量库、对象存储、消息队列）通过稳定接口调用；
- 说清楚 **同步调用 vs 异步任务** 的切分依据（延迟预算、失败重试）。

**常见追问：**

- 团队很小、没有平台组时，边界会不会变？怎么避免过度拆分？

### Q17. Parent-Document Retriever 能力要上生产，你会优先保证哪三件事？ {#q17}

| 维度 | 说明 |
|------|------|
| 类型 | 生产化 |
| 难度 | 高频 |
| 考点 | 生产落地 |

**参考答法（开发向）：**

结合 Parent-Document Retriever 常见风险点：**Parent-Document Retriever**（父文档检索器）：一种 RAG 索引策略——将文档先切成较大的 **父块**（Parent Chunk，通常对应章节），再在每个父块内切成较小的 **子块**（Child Chunk）仅用于 **向量检索**；检索命中子块后，取出关联 **父块全文**（或更大上下文）交给 LLM 生成答案。 通俗说：**用「小纸条」找位置，用「整页纸」给模型读**——检索找得准，生成读得全。

**推荐三件事**：
1. **SLO 与降级**：定义 P95/P99、错误预算；检索失败/模型超时时的兜底路径；
2. **可观测**：trace_id 贯穿；记录检索命中、token、工具调用、人工介入；
3. **变更安全**：配置与 Prompt 版本化；灰度 + 自动回滚条件；回归评测门禁。

面试时用 **一个真实指标** 收尾（如 citation 准确率、empty retrieval 率）。

**常见追问：**

- 如何做成本归因到租户/业务线？
- on-call 值班最需要哪三张大盘？
